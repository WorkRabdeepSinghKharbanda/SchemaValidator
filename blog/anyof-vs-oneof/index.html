anyOf vs oneOf in JSON Schema: what's the difference

anyOf means "at least one of these must match." oneOf means "exactly one of these must match." That one word — "at least" vs "exactly" — is the entire difference, and it trips people up constantly.

New to JSON Schema? Start with What is a JSON Schema? A beginner's guide first.

What each keyword actually checks

Both anyOf and oneOf take an array of subschemas. A value is valid under anyOf if it matches one or more of the listed subschemas — matching two or three of them is still a pass. A value is valid under oneOf only if it matches exactly one of the listed subschemas — matching two of them is a failure, the same as matching zero.

A concrete example where they disagree

Take this schema fragment, used with both keywords:

{
  "anyOf": [
    { "type": "number" },
    { "type": "integer" }
  ]
}

The value 5 is a number and an integer — it matches both subschemas. Under anyOf, that's fine: at least one matched. Under oneOf, swapping in the same two subschemas, 5 would fail, because it matched two branches instead of exactly one. This is the single most common cause of a confusing "valid-looking data failed validation" bug — a schema author used oneOf intending "pick one of these shapes," not realizing their branches weren't mutually exclusive.

How to check which one your schema actually needs

  1. Open Schema Validator and paste your schema with the ambiguous anyOf/oneOf block.
  2. Paste a value you expect to match more than one branch.
  3. If it's currently oneOf and that value unexpectedly fails, that's the exact symptom described above — your branches overlap.
  4. Either switch to anyOf (if "matches more than one branch" is actually fine) or tighten the branches so they're mutually exclusive (if you really do want exactly-one semantics).

When to reach for each one

  • Use anyOf when a value can legitimately satisfy more than one of the listed shapes and that's fine — e.g. "a string, OR a number, OR an array of strings," where the branches don't overlap but you're not relying on exclusivity as a rule.
  • Use oneOf when you specifically want to enforce that a value matches exactly one variant and not several — a tagged union / discriminated type, where matching two branches would indicate an ambiguous or malformed value you want to reject.
  • If you're not sure which you want, anyOf is usually the safer default — it's less likely to reject data you didn't expect to reject, since it only requires one match rather than exclusivity.

Where this goes wrong in practice

The failure mode is almost always the same shape: someone writes a oneOf with branches that look mutually exclusive on paper (a "circle" shape vs. a "square" shape) but actually overlap because a required discriminator field was left optional, or a loosely-typed branch (like a bare { "type": "object" } with no further constraints) accidentally matches everything. The fix is almost never "give up on oneOf" — it's adding a required discriminator field (like "type": "circle" as a const) to each branch so they genuinely can't overlap.

Everyday use cases

  • A field that accepts either a string or an array of strings — anyOf, since the two shapes don't overlap but there's no need to enforce exclusivity.
  • A discriminated union — e.g. a "shape" object that's either a circle (radius) or a rectangle (width/height) — oneOf with a discriminator field in each branch, so a malformed object matching both (or neither) correctly fails.
  • An API field that's loosening over time from one fixed shape to "the old shape or the new shape" — anyOf, so either is accepted during the transition without worrying about overlap.
  • Validating a webhook payload that could be one of several distinct event types — oneOf with each event type requiring a literal "type" value, so an ambiguous payload is rejected rather than silently matching the wrong handler's expectations.

Fixing an overlapping oneOf with a discriminator

Here's the shape-union example made concrete, with the bug and the fix side by side:

// Before — ambiguous, both branches can match an object with no extra fields
{
  "oneOf": [
    { "type": "object", "properties": { "radius": { "type": "number" } } },
    { "type": "object", "properties": { "width": { "type": "number" }, "height": { "type": "number" } } }
  ]
}

// After — a required, literal discriminator makes the branches mutually exclusive
{
  "oneOf": [
    {
      "type": "object",
      "properties": { "kind": { "const": "circle" }, "radius": { "type": "number" } },
      "required": ["kind", "radius"]
    },
    {
      "type": "object",
      "properties": { "kind": { "const": "rectangle" }, "width": { "type": "number" }, "height": { "type": "number" } },
      "required": ["kind", "width", "height"]
    }
  ]
}

The "before" version can fail in a surprising way: an object like {} (no properties at all) satisfies both branches' properties constraints trivially, since neither branch requires anything — so it matches both and fails oneOf, even though it looks like it matches neither. Adding a required kind discriminator with a const value to each branch fixes this: now exactly one branch can match any given object, by construction.

What the error message actually tells you

When a value fails a oneOf check in ajv (the validator this app uses), the error reported is often just "must match exactly one schema in oneOf" — it doesn't by default tell you which branches matched or didn't, or whether the failure was zero matches or multiple matches. That ambiguity is exactly why checking the branches by hand (as in the earlier example) is often faster than trying to debug from the error message alone — paste your schema and a borderline value into a validator, and see directly which branches it does and doesn't satisfy.

Common mistakes

The single most common mistake is reaching for oneOf by habit (it "sounds" like the right keyword for "this or that") without checking whether the branches can actually overlap. A close second: forgetting that allOf is a third, different keyword — "the value must match every listed subschema" — easy to confuse with the other two by name alone.

Frequently asked questions

What's the actual difference between anyOf and oneOf?

anyOf requires at least one subschema to match; oneOf requires exactly one. A value matching two or more branches passes anyOf but fails oneOf.

Why is my valid-looking data failing a oneOf check?

It's almost certainly matching more than one of the listed branches — check whether your branches genuinely are mutually exclusive, and add a discriminator field if not.

Is allOf related to this?

It's a third, different keyword: allOf requires a value to match every listed subschema, not just one or exactly-one.

Which one should I default to if I'm not sure?

anyOf is usually the safer default — it won't reject data just because it happens to match more than one branch.

Can I test this against my own schema?

Yes — paste your schema and a borderline value into Schema Validator and see which keyword actually produces the result you expect.
