Common JSON Schema mistakes a linter catches (that validation won't)

A schema that compiles fine can still be quietly wrong in ways that only surface later, as a confusing bug report.

New to JSON Schema? Start with What is a JSON Schema? A beginner's guide first.

What it is

Validation and linting answer different questions. Validation asks "does this data satisfy this schema?" Linting asks "is this schema itself well-formed, in ways that won't show up as a validation error at all?" A schema can be perfectly valid JSON Schema — ajv compiles it without complaint — and still contain a mistake that quietly breaks your intent for every record that passes through it.

Schema Validator's linter runs a small, deliberately conservative set of checks against the current schema: a required entry that doesn't appear anywhere in properties (this one can never pass, for any input — it's flagged as a warning, not a suggestion), an object schema with additionalProperties left unset (which silently accepts extra, unexpected fields, including a typo'd version of a real field name), and an enum with exactly one allowed value (almost always meant to be const instead, which states the same constraint more clearly). The linter recurses into nested properties and array items up to a depth of six levels, and deliberately skips over $ref nodes rather than trying to resolve and re-check them. Results appear in a collapsible panel below the schema summary, so they're visible without getting in the way when you don't need them.

How to use it

  1. Paste or write your schema in Schema Validator's schema pane — no data is required for linting to run.
  2. Open the JSON Schema Linter panel below the schema summary; it expands automatically if there's anything to flag.
  3. Read each hint: it names the offending property path and which of the three checks triggered.
  4. Fix the schema directly in the editor and watch the hint disappear once the issue is resolved — no separate re-run step.

Benefits

The value of linting is that it catches mistakes before you ever run data through the schema — which matters because the three checks above are exactly the kind of thing that's invisible until it isn't. A required field that's never declared in properties doesn't throw a compile error; it just makes every single record fail, and the resulting ajv error ("must have required property X") looks identical to a normal validation failure, so you end up debugging the data when the schema was wrong all along. An unset additionalProperties doesn't fail anything either — it just means a typo'd field name (emial instead of email) sails through validation as an "extra" property instead of being caught as a missing one. Neither of these produces an error until you go looking for one, which is exactly why a linter that runs proactively, on the schema alone, is worth having.

Where other approaches fall short

Treating "the schema compiles" as "the schema is correct" is the most common gap here — a syntactically valid schema and a schema that expresses what the author actually meant are not the same thing, and most validators only check the former. Reading a schema by eye to catch these issues doesn't scale past a handful of properties, and gets worse exactly when it matters most: large, deeply nested schemas built up over months by more than one person, where a stray property name or a forgotten additionalProperties is easy to miss in a wall of JSON. A general-purpose JSON linter also won't help, since these are JSON Schema–specific semantic issues, not syntax issues — the JSON itself is fine; it's the meaning of the keywords relative to each other that's wrong.

Everyday use cases

  • Reviewing a schema someone else wrote before adopting it, to catch an unset additionalProperties that would otherwise let bad data slip through silently.
  • Debugging a schema where validation reports 100% failures and the cause isn't obvious — checking for a required/properties mismatch first, before suspecting the data.
  • Cleaning up a schema that's grown organically over several PRs, where a field was renamed in properties but the old name was left behind in required.
  • Tightening a schema before using it as a public API contract, where an unset additionalProperties is a much bigger risk than in an internal config file.
  • Simplifying a schema inherited from another tool's auto-generated output, where single-value enums are a common artifact of generation from example data.

Tips and common mistakes

Don't treat every hint as mandatory — the linter is about best practices, not spec compliance, and an unset additionalProperties is sometimes genuinely intentional (an evolving schema that needs to tolerate new fields from an upstream source, for instance). The one exception is the required/properties mismatch: because it can never pass for any input, there's no legitimate reason to leave it as-is, which is why it's the only one of the three shown as a warning rather than a plain suggestion.

A second common mistake is assuming lint hints mean the schema is "broken" — they don't. All three checks are advisory: the schema still compiles, and data can still validate against it. What they flag is a gap between what the schema says and what the author probably meant, which is a different, quieter kind of bug than a syntax error. That's also why the linter is conservative about what it checks at all — it deliberately avoids guessing at intent (like suggesting a format or pattern based on a property's name), sticking only to checks that are unambiguously correct regardless of context.

Frequently asked questions

Does a JSON Schema linter check the same thing as validation?

No. Validation checks whether a piece of data satisfies a schema. Linting checks the schema itself for internal inconsistencies and best-practice gaps that won't produce a validation error at all — like a required field that's never declared in properties.

Why does a schema with a required/properties mismatch still "validate" successfully?

Because ajv (and every other JSON Schema validator) only checks that the schema is syntactically well-formed when it compiles it — it has no way to know that a name in required was supposed to match one in properties. The mismatch only shows up as every record failing once you run real data through it, which is exactly the gap a linter closes earlier.

What does leaving additionalProperties unset actually do?

By default, JSON Schema object validation allows any extra properties beyond the ones listed in properties. Leaving additionalProperties unset means a typo'd field name is treated as just another extra property rather than a missing required one, so it passes validation silently instead of surfacing as an error.

Should I always set additionalProperties to false?

Not always — it depends on whether the schema needs to tolerate fields it doesn't know about yet (common for schemas consuming data from an upstream system you don't control). The linter flags it as something to consider, not something to always fix.

Why use const instead of a single-value enum?

They're functionally equivalent — both only allow one specific value — but const states that intent directly, while a single-value enum reads as if more values were originally intended and later narrowed down, which is more ambiguous for the next person reading the schema.

Does the linter resolve $ref before checking a schema?

No — nested $ref nodes are deliberately skipped rather than resolved and re-checked, so a linted schema that references another schema via $ref won't have that referenced schema's own issues surfaced here.

Is this a replacement for a full JSON Schema style guide or spec-compliance tool?

No — it's intentionally narrow: three checks that are unambiguously correct regardless of what the schema author intended, not a broader opinionated style guide. That's a deliberate scope limit, not a missing feature.
