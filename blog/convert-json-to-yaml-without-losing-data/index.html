Convert JSON to YAML (and back) without losing data

A naive JSON↔YAML conversion usually works — until a type, an anchor, or a multiline string doesn't round-trip the way you expected.

New to JSON Schema? Start with What is a JSON Schema? A beginner's guide first.

What it is

Converting between JSON and YAML means parsing one format into an in-memory data structure, then serializing that structure back out in the other format. The data itself doesn't change — only its textual representation does — but a few of YAML's features don't have a clean one-to-one JSON equivalent, which is where naive conversions quietly lose fidelity. YAML supports unquoted strings that look like numbers or booleans (a version string like 1.0 can silently become a float if it isn't quoted), multiline block scalars for long strings, and anchors/aliases that let one block of YAML reference another instead of repeating it. JSON has no native equivalent for anchors, so converting YAML → JSON → YAML again can flatten an anchor into a repeated literal block — usually harmless, but worth knowing before you assume a round-trip preserved everything exactly as written.

How to use it

  1. Open Schema Validator and paste your JSON (or YAML) into the data pane.
  2. Use the format tabs' convert button to switch the target format — JSON, YAML, TOML, XML, or CSV — in place, in the same pane.
  3. Check the converted output for anything format-specific that needed to change shape, like a YAML anchor becoming a literal block.
  4. Validate the converted result against your JSON Schema immediately, in the same pane, rather than treating conversion and validation as two separate manual steps.
  5. If validation fails on the converted output but passed on the original, that's a signal the conversion changed something's type or shape — check the specific field the error points to.

Benefits

Converting programmatically instead of by hand removes the most common source of round-trip errors: manually retyping indentation, quoting, or punctuation when translating between two very differently-structured text formats. Checking the result against a schema right after converting also catches a problem immediately, at the point it was introduced, rather than three steps downstream where it surfaces as a confusing, hard-to-trace bug in whatever system consumes the converted file. Because the conversion and the validation happen in the same pane, there's no copy-paste between separate tools where a stray character could get dropped or an unsaved edit could get lost.

Where other approaches fall short

A generic online format converter typically stops at producing output text — it has no way to tell you whether that output is actually correct for your use case, only that it's syntactically valid YAML or JSON. That means a silently-changed type (a version string that became a float, a quoted number that lost its quotes) passes through without any signal that something's different, since syntactic validity and semantic correctness are two different things. Manually converting by hand is slower and more error-prone the larger the document gets, especially with YAML's indentation-sensitive syntax, where a single misplaced space changes the structure rather than just failing to parse.

Everyday use cases

  • Converting a JSON config file to YAML for a tool or platform (like many CI systems and Kubernetes) that expects YAML config.
  • Converting a YAML manifest back to JSON to feed into a tool or script that only accepts JSON input.
  • Checking that a config migrated from JSON to YAML (or the reverse) still validates against the same schema after conversion.
  • Quickly previewing what a JSON API response or payload would look like in YAML, for documentation or a more readable review.
  • Converting sample data between formats while testing a schema that needs to support more than one serialization format.

Tips and common mistakes

Don't assume a round-trip (JSON → YAML → JSON) is automatically lossless — it usually is for plain data, but YAML-specific features like anchors and block scalars don't always survive the round-trip in their original form. If a converted value matters precisely (a version string, an ID that looks numeric), check it explicitly rather than assuming the converter guessed the right type.

Quoting matters more in YAML than people expect coming from JSON, where every string is already delimited by double quotes and there's no ambiguity. A bare yes, no, on, or off in YAML can be interpreted as a boolean rather than a string under some YAML parsers, the same way an unquoted 1.0 can become a float — if a field needs to stay a literal string no matter what it looks like, quote it explicitly in the YAML rather than relying on the converter to guess your intent correctly every time.

Frequently asked questions

How do I convert JSON to YAML without losing data?

Convert programmatically rather than by hand, then validate the result against the same JSON Schema used for the original data — that catches a type or structure change immediately instead of it surfacing later. Schema Validator's format converter does the conversion and lets you validate in the same pane.

Can I convert YAML back to JSON, not just JSON to YAML?

Yes — conversion works both directions, along with TOML, XML, and CSV, since all five formats parse into the same in-memory data structure before being serialized back out in the target format.

Why did my version number change when I converted JSON to YAML?

An unquoted value that looks numeric in YAML (like 1.0) can be interpreted as a float rather than a string, which changes it if the original was meant to stay a literal version string. Quote it explicitly in the YAML source, or check the converted output against a schema that expects a string.

Do YAML anchors and aliases survive a JSON round-trip?

No — JSON has no equivalent of a YAML anchor/alias, so converting YAML to JSON and back to YAML again can expand an anchor into a repeated literal block instead of a reference. The data itself is unchanged, but the anchor structure doesn't make the round-trip.

How do I check that my converted YAML is still valid against my schema?

Run it through JSON Schema validation right after converting, using the same schema you validated the original JSON against. If the converted data still validates, the conversion didn't change anything the schema cares about.

Can I convert JSON to formats other than YAML, like TOML or CSV?

Yes — the same converter switches between JSON, YAML, TOML, XML, and CSV, since all five parse into the same underlying data structure before being serialized back out. The conversion mechanics (and the "validate after converting" advice) apply the same way regardless of which two formats you're converting between.
