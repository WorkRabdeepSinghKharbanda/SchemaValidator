Fixing common JSON syntax errors: trailing commas, single quotes, unquoted keys

JSON is strict on purpose, but the mistakes that break it are almost always the same handful, every time.

What it is

JSON looks almost identical to a JavaScript object literal, which is exactly why it's so easy to write invalid JSON without noticing: a trailing comma before a closing } or ], single-quoted strings instead of double, and unquoted object keys ({ name: "value" }) are all valid JavaScript and all rejected by a strict JSON parser. Beyond those three JS-isms, a dropped comma between two properties or an unterminated object or array are the other common way hand-edited or hand-copied JSON breaks — structural gaps rather than stylistic ones.

A JSON repair tool fixes all of these: trailing commas, single quotes, unquoted keys, a missing comma, or a missing closing bracket. What it can't do, and shouldn't try to, is fix a value that's syntactically fine but semantically wrong — a string sitting where a number belongs, or a required field that's simply missing. That's schema validation's job, not repair's: repair gets you to parseable JSON, validation tells you whether that JSON is the JSON you actually meant to write.

How to use it

  1. Paste the broken JSON into Schema Validator's data pane and try to validate it — a plain parse error (not a schema mismatch) means the JSON itself isn't valid yet.
  2. Click the auto-fix button that appears alongside the parse error. This only runs for JSON data with a plain syntax error, so it won't fire for YAML/TOML/XML/CSV or for schema-mismatch errors where the JSON already parses fine.
  3. Review the repaired JSON in the data pane — trailing commas, single quotes, unquoted keys, and small structural gaps like a missing comma or bracket are fixed automatically.
  4. If the fix isn't what you wanted, click Undo — it's a one-click action, not a "redo it by hand" situation.
  5. Run Validate again, now against your actual JSON Schema, to catch anything repair can't: a wrong type, a missing required field, an out-of-range value.

Benefits

All of these mistakes are mechanical, predictable transformations — exactly the kind of thing worth automating instead of scanning a large file character by character for the one comma that broke everything. Fixing the syntax first, separately from schema validation, also means the two failure classes don't get confused: a parse error and a "this field should be a number" error look completely different and call for different fixes, and keeping them as two distinct steps makes it obvious which one you're looking at.

Where other approaches fall short

A strict JSON parser, by design, gives you no more than "unexpected token" and a character offset — accurate, but not actionable if you don't already know what's wrong. Manually scanning for a stray trailing comma in a large config file or API response is slow and error-prone, especially once the file is long enough that the error isn't near either end. Some editors offer JSON-with-comments or JSON5 modes that happen to tolerate trailing commas, but that just relocates the problem: the file still isn't valid JSON the moment something downstream (an API, a strict parser, a CI check) expects the real spec.

Everyday use cases

  • Cleaning up a config file someone hand-edited in a JS-aware editor that silently tolerated a trailing comma.
  • Fixing a JSON blob copy-pasted out of a JavaScript source file, where single quotes and unquoted keys came along for the ride.
  • Repairing an API response saved to a file by hand (or truncated mid-copy) before feeding it into another tool that requires strict JSON.
  • Recovering a JSON document that's missing a closing bracket because an edit was interrupted partway through.
  • Quickly fixing sample data before running it through schema validation, so the first error you see is an actual schema mismatch, not a stray comma.

Tips and common mistakes

Don't assume repair fixed everything just because the file parses afterward — a repaired file is syntactically valid JSON, not necessarily correct JSON. Always run it through schema validation next if you have a schema, since repair has no way to know a field's value should've been a number instead of the string it happily parsed.

Another common mistake is trying to fix the syntax error by eye first and only reaching for a repair tool once that fails — for anything beyond a single obvious typo, it's faster to let the repair tool make a first pass and then review the diff than to scan a large file character by character looking for one dropped comma. And if a file won't parse at all even after repair, that usually means the structural damage is more severe than a trailing comma or a missing bracket — a genuinely truncated file, or binary data mistaken for text — which repair tools aren't designed to reconstruct.

Frequently asked questions

What's the most common JSON syntax error?

Trailing commas before a closing } or ] — a holdover from copying or writing JSON like a JavaScript object literal, which tolerates them where strict JSON does not.

Can a JSON repair tool fix a missing comma or bracket, not just quotes?

Yes — beyond trailing commas, single quotes, and unquoted keys, repair also handles some structural gaps: a comma dropped between two properties, or an unterminated object or array.

Will JSON repair fix a value that's the wrong type?

No. Repair only fixes syntax — it can't tell that a string should've been a number, or that a required field is missing, because those are semantically wrong, not syntactically broken. Run the repaired JSON through schema validation to catch that class of problem.

Why does my JSON fail to parse when it looks fine in my editor?

Many code editors render JavaScript-flavored JSON (trailing commas, single quotes, comments) without complaint, since they're often in a more lenient JS/JSON5-aware mode. A strict JSON parser enforces the actual spec and will reject the same text.

Is there a command-line or IDE version of this JSON repair tool?

No — this is a browser-based tool with no CLI or IDE plugin. If you need the same fix inside a script or CI pipeline, use the schema pane's "Copy as Node.js/Python snippet" feature to get a self-contained script you can run outside the browser.

Can I undo an auto-fix if it changes something I didn't intend?

Yes — auto-fix is a one-click action with a one-click undo, so reverting an unwanted repair doesn't mean retyping the original by hand.

Does JSON repair work on YAML, XML, or CSV too?

No — auto-fix is specifically for JSON data with a plain parse error. Other formats have their own parsers and their own error conventions; a YAML or TOML parse error surfaces the library's own error message rather than going through the same repair step.
