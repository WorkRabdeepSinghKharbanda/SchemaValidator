How to generate a JSON Schema from an example payload

Writing a schema from scratch for data that already exists is backwards — infer a draft from the data, then refine it.

What it is

JSON Schema generation from an example payload is the process of reading a real piece of JSON — an API response, a config file, a database export — and producing a JSON Schema document that describes its shape: which properties exist, what type each one is, and how they nest. Instead of opening a blank editor and typing out type, properties, and nesting by hand, you paste data you already have and get a starting schema back.

This is schema inference, not validation. It doesn't check whether your data is correct against some rule set — there isn't one yet. It looks at one concrete example and generalizes a structural description from it. The output is a draft, grounded in draft-07, 2019-09, or 2020-12 JSON Schema depending on what you select, and it's meant to be reviewed and tightened, not used verbatim.

How to use it

  1. Open the JSON Schema Generator or the main Schema Validator app.
  2. Paste your example payload into the data pane — this can be a single object or an array.
  3. Pick the JSON Schema draft you need (draft-07, 2019-09, or 2020-12) from the toolbar dropdown.
  4. Run the inference — the generated schema is written directly into the schema pane, ready to edit.
  5. Review every field: mark the ones that must always be present as required, and add constraints (pattern, minimum, enum) the inference couldn't know to add.
  6. Validate other sample payloads against the draft schema in the same tool to confirm it generalizes the way you expect.

Benefits

The main benefit is speed: a schema for a payload with twenty fields takes seconds to draft instead of minutes of manual typing, and you start from something that already matches your real data instead of guessing at field names and types from memory or documentation that may be stale. It also reduces a specific class of mistake — a hand-typed schema can easily use the wrong type for a field (a string instead of a number, say) if you're working from a spec rather than the actual payload; inference reads the type straight from the value.

It's also a useful sanity check in the other direction: generating a schema from a payload and comparing it against an existing hand-written schema for the same endpoint can surface fields the hand-written version missed or typed incorrectly.

Where other approaches fall short

Writing a schema by hand from documentation alone means trusting that the docs are accurate and current — they frequently aren't, especially for internal or undocumented APIs. Copying an existing schema from a similar endpoint and editing it by hand carries over assumptions that may not hold for the new data. And some tools that generate schemas from JSON examples are narrowly scoped to one draft version or don't let you pick a target draft at all, which matters if your validator or downstream tooling expects a specific one.

Everyday use cases

  • You're integrating a third-party API with thin or outdated documentation and want a schema that reflects what the API actually returns today.
  • You're writing a contract test between two services and need a baseline schema to start tightening into an explicit contract.
  • You inherited a config file format with no schema at all and want a starting point for validating future changes to it.
  • You're migrating a data export (a CSV turned into JSON, or a database dump) into a system that requires schema validation on ingest.
  • You want a quick second opinion on whether a hand-written schema actually matches a real payload, by diffing the inferred version against it.

Tips and common mistakes

The biggest mistake is treating the generated schema as final. Inference describes one example, not every valid case — it has no way to know that a field is optional if your one sample happened to include it, or that a number can go negative if your sample was always positive. Always pass in a representative sample, and if you can, generate from a few different payloads and merge the results by hand rather than relying on just one.

A second common mistake is picking the wrong target draft after the fact. If your downstream validator or tooling expects draft-07 specifically, set that before generating rather than generating against the default and switching later — switching drafts doesn't retroactively rewrite keywords that behave differently between versions, so it's worth getting it right up front. If your schema was authored elsewhere and already declares a $schema URI, the validator can also auto-detect the draft from that URI and switch the dropdown to match, which is a useful double-check that you're editing with the right draft's rules in mind.

Once you have a draft schema, don't stop at generating it — paste a second, different example of the same kind of data back in as the data pane's content and validate it against the schema you just generated. This surfaces fields the first example didn't exercise (an optional field that was missing, a value with a different type than expected) faster than reading the schema line by line.

A note on nested structures

Inference works through nested objects the same way it works at the top level — each nested object's properties and types are read directly from the sample — but the array caveat compounds with nesting. An array of objects, each containing its own nested array, only has its outer shape inferred from the first element, and that first element's own nested array is in turn only inferred from its first element. For deeply nested sample data with variable inner structure, it's worth generating a schema from more than one example and comparing the nested portions by hand, rather than assuming one pass captured every variation.

Frequently asked questions

Can this generate a draft-7 JSON Schema specifically?

Yes — the draft dropdown lets you choose draft-07, 2019-09, or 2020-12 before generating, so the output targets whichever draft your validator or tooling expects.

Does this also generate a UI form from my schema?

No. This tool generates a JSON Schema from example data — it doesn't turn a schema into a rendered form. If you're looking for a form-builder that reads a JSON Schema, that's a different kind of tool than this one.

How does it handle arrays?

An array's shape is inferred from its first element only. If your array mixes items with genuinely different shapes, the generated items schema will reflect just the first one — review it by hand rather than trusting it blindly. This is a documented limitation, not a bug that might get silently "fixed" later.

Will the generated schema mark fields as required?

Inference can't tell whether a field is required just from one example — it has no way to distinguish "always present" from "happened to be present in this sample." Review and set required yourself based on what you actually know about the data.

Can I generate a schema from an array of records instead of a single object?

Yes, you can paste an array — keep in mind the "first element only" rule above applies to the array's own shape, so if different records vary meaningfully, generate from a few individually and compare.

Does this replace writing a schema by hand entirely?

No — it replaces the blank-page part. You still need to review the result and add the constraints (required fields, patterns, ranges) that reflect your actual intent, since inference only sees the one example you gave it.

Is this the same as JSON-to-TypeScript conversion?

No. This generates a JSON Schema from example data; converting a JSON Schema into a TypeScript interface is a separate step, covered in this post.
