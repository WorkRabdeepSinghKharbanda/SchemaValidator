Auto-generate sample test data from a JSON Schema

A hand-written test fixture can silently drift out of sync with the schema it's supposed to satisfy. Generated fixtures can't.

What it is

Sample data generation from a JSON Schema does the reverse of schema inference: instead of reading real data to produce a schema, it reads a schema and produces fake data that is guaranteed to satisfy it. Give it an object schema with properties, types, and constraints, and it returns a concrete JSON value — strings, numbers, nested objects, arrays — shaped exactly the way the schema describes.

Because the output is generated from the schema itself at the moment you run it, it reflects whatever the schema currently says, not whatever someone remembered when they last wrote a fixture by hand. That single property is the whole point of the feature.

How to use it

  1. Open the Sample JSON Generator or the main Schema Validator app.
  2. Paste or write your JSON Schema into the schema pane.
  3. Generate a single sample record from the pane's menu, or switch on batch mode to generate many at once.
  4. In batch mode, choose a count (up to 500 records in one run) when prompted.
  5. Copy the output, or export it as JSON or CSV depending on what your test setup expects.
  6. Re-run generation any time the schema changes, instead of hand-editing an old fixture to match.

Benefits

The core benefit is that generated fixtures can't drift out of sync with the schema — there's no stale copy sitting in a test file from six months ago, because you regenerate it from the current schema whenever you need it. This removes an entire class of flaky test failure where the fixture itself is the thing that's wrong, not the code under test.

It also saves the manual effort of writing realistic-looking values for every field of a schema with many required properties, nested objects, and enums — especially useful when a test just needs valid data and the actual values don't matter.

Where other approaches fall short

Hand-maintained fixtures require someone to notice a schema change and go update every fixture file that depends on it — a step that's easy to skip under deadline pressure and has no automatic check forcing it to happen. Writing a one-off script to generate fake data per project means maintaining yet another piece of code, and it typically doesn't stay schema-aware as the schema evolves. Fixtures copied from production data carry privacy and compliance risk that generated-from-schema data simply doesn't have, since nothing in it is real.

Everyday use cases

  • Seeding a local or test database with records that satisfy your current schema, without hand-writing each row.
  • Stress-testing a batch import pipeline with hundreds of generated records at once.
  • Producing a quick example payload to hand to a frontend developer who's building against an API contract that isn't live yet.
  • Refreshing stale test fixtures after a schema change, instead of manually patching each one.
  • Demoing an API or form to a stakeholder with plausible-looking data when no real data is available or appropriate to show.

Tips and common mistakes

Generated data satisfies the schema's structural constraints, but it's synthetic — don't mistake it for data that's realistic in a business sense (a generated email string, for instance, is valid per a format check but not necessarily a real address). For tests that care about specific values, use generation to get the shape right and then adjust individual fields by hand rather than regenerating and hoping for a specific value to come up.

Another common mistake is generating once and reusing the same fixture indefinitely anyway — which quietly recreates the original problem if the schema later changes and nobody re-runs generation. Treat generation as something you re-run on demand, not a one-time export. Because it's cheap to regenerate, there's no real cost to doing this every time the schema changes rather than only when a test starts failing.

If a generation run produces data you don't expect — a field missing, or a value that doesn't look like what the schema seems to describe — check the schema itself first. A loosely constrained schema (a string with no format or pattern, a number with no minimum/maximum) can only produce loosely constrained sample data; tightening the schema tightens what comes out of generation, for free.

Single sample vs. batch generation

Single-sample generation is the right tool for a quick example payload — demoing an API, showing a frontend developer what a response will look like, or getting one valid record to hand-edit into a specific test case. Batch generation (up to 500 records) is for anything that needs volume: seeding a database, exercising a batch-import pipeline, or generating enough variety that edge cases in your code show up across the set rather than relying on one example to catch everything. Both pull from the same underlying schema-to-data generation, so a batch run is not a different feature with different guarantees — it's the same guarantee, repeated.

Frequently asked questions

Is this an exact match for "sample JSON generator from schema"?

Yes — generating a sample JSON document directly from a JSON Schema, rather than from an example payload, is exactly what this feature does.

How many sample records can I generate at once?

Batch generation is capped at 500 records per run, which is a practical UX limit rather than a hard technical ceiling — it keeps a single generation request fast and the output manageable to review.

Does the generated data always pass validation against the same schema?

Yes — that's the guarantee. The data is built from the schema's own constraints, so validating it back against that same schema should always succeed, barring a schema feature the generator doesn't support.

Can I generate data in formats other than JSON?

The data pane supports JSON, YAML, TOML, XML, and CSV for editing and conversion, so you can generate a sample and then convert or export it into whichever of those formats your test setup needs.

Will this generate data that looks realistic, like real names or addresses?

It generates values that satisfy the schema's types and constraints (a format: email string that looks like an email, for example), not data drawn from real-world datasets. Treat it as structurally valid, not business-realistic.

What happens if I edit the schema while a generation is in progress?

The generator snapshots the schema before it starts and checks it hasn't changed before applying the result, so an in-flight generation can't silently overwrite an edit you made to the schema or data pane while it was running.

Can I undo a generated sample if it overwrites my existing test data?

Yes — generating a sample (single or batch) is one of the actions with a one-click Undo in the success toast, which restores exactly what was in the editor beforehand.

Does generated data work for batch validation testing too?

Yes — generating a batch of records pairs naturally with the validator's own batch mode, which checks each item of an array independently and reports pass/fail per row, useful for confirming a batch-import pipeline handles a large set of schema-valid records correctly.
