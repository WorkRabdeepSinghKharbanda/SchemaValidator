How the JSON Schema `pattern` keyword actually works

`pattern` is just a regular expression tested against a string value — but a few gotchas trip people up regularly.

What it is

The pattern keyword constrains a string-typed schema value by regular expression: a value is valid only if the regex matches somewhere in it. That sounds simple, but two things trip people up constantly. First, it's unanchored by default — unlike some regex contexts, a pattern like [0-9]+ matches if it appears anywhere in the string, not the whole thing, so it happily matches "abc123def" unless you anchor it yourself with ^ and $. Second, pattern is defined against the ECMA-262 regular expression dialect — the same one JavaScript uses — not PCRE, POSIX, or any other language's regex flavor. Named capture groups, lookbehind, and other dialect-specific features may behave differently, or not be supported at all, depending on which language's validator is compiling the pattern.

When a pattern-keyword validation fails, the ajv error tells you the value didn't match — not why, and not what would have matched. Benefits

Testing against the schema's real, exact pattern string — not a pattern you've retyped from memory into a separate tool — removes an entire class of "it works in the regex tester but not in validation" confusion, which usually comes down to a copy-paste mismatch or a subtly different escaping. Because the test runs with new RegExp, a second, independent parse of the same string ajv already compiled once, a pattern that's somehow not valid JavaScript regex syntax fails gracefully (the tester returns no match rather than throwing), instead of surfacing as a confusing crash.

Where other approaches fall short

A generic online regex tester, used without JSON Schema context, has two problems. The language/dialect selector matters more than it looks: many regex testers default to a different engine (PCRE, Python's re, .NET), and a pattern that behaves one way there can behave differently under the ECMA-262 rules JSON Schema actually specifies — lookbehind support and named-group syntax are common places this bites. The second problem is pure friction: round-tripping a pattern string out of your schema, into a separate tab, and a fix back in, loses the actual failing value and the actual validation error you were trying to debug, so you're testing in the abstract instead of against the specific case that failed.

Everyday use cases

  • Debugging why a seemingly correct-looking email or phone-number pattern rejects a value you expected to pass.
  • Writing a new pattern for a field like a SKU or an ID format and checking it against a handful of real and edge-case examples before saving the schema.
  • Porting a regex from another language's codebase into a JSON Schema and confirming it still behaves the same way under JS regex semantics.
  • Diagnosing a pattern that's unintentionally too permissive because it's missing ^/$ anchors, letting values with extra characters slip through.
  • Checking a pattern against a batch of sample values quickly before committing to it as part of a schema that will gate real data.
  • Reviewing an inherited schema written by someone else, where the pattern's purpose isn't obvious from the property name alone, by feeding it a few representative values and seeing what it actually accepts.

Where pattern fits among JSON Schema's string constraints

pattern is one of several ways to constrain a string value, alongside format (a named, semantic check like "email" or "date", whose exact enforcement depends on the validator), minLength/maxLength, and enum for a fixed set of allowed values. pattern is the right tool specifically when the valid shape is structural and can't be expressed as one of the built-in named formats — a product code with a fixed prefix and digit count, for instance, where format has no matching option and an enum would be impractically large.

Tips and common mistakes

The single most common mistake is assuming pattern matches the whole string the way some other validation frameworks do by default — it doesn't, so forgetting ^ and $ anchors is the most frequent cause of a pattern silently accepting more than intended. The second most common mistake is writing and testing a pattern in a different regex dialect (commonly PCRE, from testing in a non-JS tool) and assuming it'll behave identically under JSON Schema's ECMA-262 requirement — it usually does for simple patterns, but diverges on features like lookbehind or possessive quantifiers.

A third, subtler mistake is forgetting that JSON itself requires backslashes to be escaped. A pattern like \d+ has to be written as "\\d+" inside the JSON schema text, since a single backslash followed by d isn't a valid JSON string escape on its own. It's easy to write a pattern that looks right when you're thinking about it as "a regex" and forget it also has to survive being embedded in a JSON string literal — this is a frequent, silent source of a pattern that matches nothing at all rather than the wrong thing, since the double-escaped sequence changes the regex itself.

It's also worth remembering that pattern only applies to string-typed values — it has no effect on numbers, booleans, or nested objects, and combining it with a type constraint of anything other than "string" is a no-op that a schema linter wouldn't catch either, since it's not one of the checks built for that purpose.

Frequently asked questions

Does JSON Schema's pattern match the whole string by default?

No. It matches if the regex matches anywhere in the string. To require a full match, anchor the pattern yourself with ^ at the start and $ at the end.

What regex dialect does JSON Schema pattern use?

ECMA-262 — the same regular expression dialect JavaScript uses. It is not PCRE, POSIX, Python's re, or any other language's regex flavor, even though many of the basics overlap.

Will a Python or Java regex tester give the same result as JSON Schema validation?

Not necessarily. Most online regex testers let you pick a language/engine, and the result can differ from JSON Schema's ECMA-262 requirement on dialect-specific features like lookbehind assertions or named capture group syntax. Test against a JS-flavored (ECMAScript) engine to match what JSON Schema validators actually use.

Why does my pattern error not explain why the value failed?

Ajv's pattern error reports that the value didn't match, not why — regex engines don't produce a diff-style explanation of a non-match. Testing the exact pattern against the failing value interactively is the practical way to see which part of the string doesn't line up.

Can I test a pattern that isn't valid JavaScript regex syntax?

The tester tries to compile it with JavaScript's own RegExp; if that fails, it reports no match rather than throwing an error, so an invalid pattern fails safely instead of crashing the page.

Does this tool test patterns against multiple regex language engines at once?

No — it tests only against the ECMA-262/JavaScript engine, which is what JSON Schema's pattern keyword is actually specified against. That's a deliberate match to the spec, not a limitation to work around.
