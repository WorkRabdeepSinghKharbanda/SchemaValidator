JSON Schema draft-07 vs 2019-09 vs 2020-12: what actually changed

A practical rundown, not a spec diff — what you'll actually run into picking a draft for a real project.

What a "draft" actually is

JSON Schema isn't one frozen spec — it's a series of dated drafts, each identified by the $schema URI at the top of a schema file (e.g. "$schema": "https://json-schema.org/draft/2020-12/schema"). Validators have to pick which draft's rules to apply, because the same keyword can mean slightly different things, or not exist at all, across drafts. That's the whole source of confusion this post exists to clear up: not "which is newest" but "which one does my schema, and the tool reading it, actually agree on."

Three drafts matter in practice today: draft-07, 2019-09, and 2020-12. Older ones (draft-04, draft-06) still show up in legacy tooling but are rarely worth targeting for anything new.

draft-07 (2018)

The most widely deployed draft, still the default in a lot of tooling and libraries. Has if/then/else conditionals and const. If a library or API you're integrating with only documents "JSON Schema" with no version, it's very likely this one.

2019-09

Split validation vocabulary out of "hyper-schema" concerns, and reworked $ref to allow siblings (in draft-07, any keyword next to a $ref was silently ignored — 2019-09 fixed that). Added unevaluatedProperties/unevaluatedItems for validating what's left over after allOf/conditionals run. Saw less real-world adoption than draft-07 or 2020-12 — it was a relatively short-lived stepping stone.

2020-12 (current)

The current stable draft. Reworked how items/prefixItems express tuple-style arrays (a breaking change from draft-07's array-form items), and refined $dynamicRef/$dynamicAnchor for extensible vocabularies. This is the right default for a new schema with no compatibility constraint.

How to use this when checking your own schema

  1. Open Schema Validator and paste your schema into the schema pane.
  2. If the schema has a $schema field with a recognized draft URI, the draft dropdown auto-switches to match and a toast confirms which draft it detected — no manual guessing.
  3. If there's no $schema field (common in hand-written or older schemas), pick a draft from the dropdown yourself, based on which library or API you're targeting.
  4. Validate a sample payload against it and check the error messages — if a keyword you expect to work is silently ignored, that's usually a sign the selected draft doesn't support it the way you think.

Why the draft you pick actually matters

The array-items change between draft-07 and 2020-12 is the one that bites people most: in draft-07, items as an array meant "validate each position against the corresponding sub-schema." In 2020-12, that same tuple-validation job moved to prefixItems, and items went back to meaning "validate every element against one schema." If you paste a draft-07-style tuple schema into a 2020-12 validator without translating it, it won't error — it'll just validate something other than what you intended, which is worse than an error, since nothing tells you it's wrong.

Picking the wrong draft for a given schema doesn't always fail loudly. Most of the time it fails quietly: a keyword gets ignored, a constraint you thought was enforced isn't, and the first time you notice is when bad data gets through that a correctly-drafted schema would have caught.

Where a mismatched draft causes real problems

Online validators and documentation examples don't always say which draft they're demonstrating, and schema authoring tools sometimes default to whatever draft they shipped with years ago rather than the current one. A generic "paste JSON, see if it's valid" checker that has no concept of drafts at all can't catch this kind of mismatch — it'll happily accept a 2020-12 schema being validated under draft-07 assumptions, because syntactically both are just JSON. The failure only shows up in what actually gets allowed or rejected at validation time, not in whether the schema document itself parses.

Everyday situations where this comes up

  • Copying a schema example from a blog post or Stack Overflow answer without checking which draft it was written against, then wondering why a keyword "doesn't work."
  • Upgrading a codebase's validation library (e.g. a new ajv major version) and discovering it defaults to a newer draft than schemas were authored for.
  • Inheriting a schema file with no $schema field at all and having to reverse-engineer which draft it targets from the keywords it uses.
  • Writing a new schema from scratch with no external constraint — the easy case, just use 2020-12.
  • Integrating against a third-party API's published schema and needing to match its draft exactly so your local validation agrees with theirs.

Tips and common mistakes

Always put an explicit $schema field in schemas you author — it costs one line and removes all ambiguity for the next person (or tool) that opens the file. Don't assume "no errors" means "same validation behavior" across drafts — the array-items case above is exactly this trap. And when in doubt, validate a known-good and a known-bad sample payload under both drafts you're considering; if the results differ, that difference is exactly what you need to understand before shipping.

Which one should you pick?

  • New project, no constraints: 2020-12.
  • Integrating with an existing API/tool that documents a specific draft: match it exactly — the array-items change between draft-07 and 2020-12 in particular will silently validate the wrong thing if you guess wrong.
  • Not sure which draft a schema was written for: check its $schema field — Schema Validator reads it and auto-selects the matching draft for you.

Frequently asked questions

What does the $schema field actually do?

It's a URI identifying which JSON Schema draft the rest of the document should be interpreted under. A validator reads it to decide which keyword meanings and validation rules apply — it's metadata about the schema, not a constraint checked against your data.

Is draft-07 deprecated?

No. It's not the current draft, but it's still extremely widely used and well supported by every major validation library. "Older" isn't the same as "unsupported" here.

Can I mix drafts, like using a draft-07 schema with a 2020-12 $ref target?

In general, no — treat a schema document and everything it references via $ref as needing to agree on draft. Mixing drafts across a $ref boundary is a common source of subtle bugs and isn't something most validators resolve for you automatically.

Will my schema just throw an error if I pick the wrong draft?

Not necessarily. Many draft differences change what a keyword means rather than making it invalid — the array-items/prefixItems change is the clearest example. The schema still "works," it just validates something other than what you intended, with no error to flag it.

Does 2019-09 still matter if almost nobody targets it directly?

Mostly for reading older schemas and understanding how unevaluatedProperties/unevaluatedItems and sibling keywords next to $ref were introduced. For new work, there's rarely a reason to pick 2019-09 over 2020-12.

How do I find out which draft a schema I didn't write was built for?

Check its $schema field first. If that's missing, paste it into Schema Validator and try validating known-good sample data under each draft candidate — differing results for the same data under different drafts tells you which one the author actually had in mind.
