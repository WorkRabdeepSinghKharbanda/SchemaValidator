Validating JSON config files in CI without a server

Design the schema interactively in a browser, then run the exact same check as a pipeline step.

New to JSON Schema? Start with What is a JSON Schema? A beginner's guide first.

The problem with "it looked fine when I checked it manually"

A schema that's only ever run by hand in a browser tab doesn't catch the config file someone edits three weeks later. You want the same check to run automatically on every pull request — but that usually means writing an ajv/jsonschema script from scratch, or standing up an API endpoint just to run a validation call. Neither should be necessary for something this small.

What this actually is

This isn't a CLI tool, a GitHub Action, or a hosted validation API — none of those are built, deliberately (adding a public API endpoint or a packaged CLI means maintaining a server or a release pipeline for something this small). What exists instead is a code generator: design and test your schema interactively in the browser, then export the exact same validation logic as a small, self-contained script you commit to your own repo and run however you like, including as a CI step.

The script isn't a wrapper around this app calling out to anywhere — it's a standalone ajv (Node) or jsonschema (Python) script with your schema and chosen draft baked directly into the source. It has no dependency on this site once generated; it runs wherever Node or Python already runs in your pipeline.

How to use it

  1. Open Schema Validator and build/paste your schema in the schema pane, picking whichever draft matches your target (draft-07, 2019-09, or 2020-12).
  2. Validate a few sample config files against it interactively until you're confident the schema actually catches the mistakes you care about.
  3. Open the schema pane's "⋯" menu and choose "Copy as Node.js snippet" or "Copy as Python snippet" — whichever matches your pipeline's existing tooling.
  4. Paste the generated script into your repo, e.g. scripts/validate-config.js, and point it at a config file path as a command-line argument.
  5. Add it as a CI step (see below) so it runs automatically on every pull request, not just when someone remembers to check by hand.

Wiring it into CI

# .github/workflows/validate-config.yml (Node example)
- name: Validate config against schema
  run: node scripts/validate-config.js config/production.json

No API call, no server round-trip — it's the same logic that already validated the file in your browser, just running as a local script. Commit the generated script alongside the schema it was generated from, and regenerate it (paste the updated schema, copy again) whenever the schema changes.

Why this is worth doing

Catching a malformed config at pull-request time is strictly cheaper than catching it at deploy time or, worse, at runtime in production. A schema check that only exists as something a person remembers to run manually will eventually get skipped — not out of carelessness, just because manual steps are the first thing to get dropped under time pressure. Making the check part of CI removes the "did anyone actually check this" question entirely: either the pipeline step passes, or the pull request is blocked.

There's also a workflow benefit that's easy to undervalue: designing the schema itself is much faster interactively, with immediate feedback on a real sample file, than it is staring at a script's error output and guessing which keyword is wrong. Doing the design work in the browser and only exporting once you're confident in the result means the script you commit to CI is already battle-tested against the config shapes you actually care about, not a first draft you're debugging live in a pipeline run.

Where other approaches fall short

Writing an ajv or jsonschema script from scratch for every config file you want to guard means hand-maintaining boilerplate (CLI argument parsing, error formatting, exit codes) that has nothing to do with the actual schema — and keeping that boilerplate in sync across multiple scripts as your validation library's API changes. Standing up an API endpoint just to run a validation call adds a server, a deployment, and a network dependency to a check that's fundamentally pure logic with no need for any of that. A purely browser-based validator with no way to export its logic solves the "did I write the schema correctly" problem but not the "does this run unattended in CI" problem — you're left re-implementing the check by hand anyway.

Everyday use cases

  • Blocking a pull request that edits a config/production.json file with a typo'd key or wrong type, before it merges.
  • Validating a generated or templated config (e.g. from a build step) matches the shape downstream code expects, as part of the build itself.
  • Checking infrastructure-as-code JSON files (feature flags, environment manifests) against a schema that encodes your team's actual constraints.
  • Running the same validation locally via a pre-commit hook and in CI, using the identical generated script in both places.
  • Giving a non-technical teammate who edits a JSON config directly a CI failure with a specific, readable error instead of a runtime crash days later.

Tips and common mistakes

Regenerate the script whenever the schema changes — it's a one-way export, not a live link, so an edited schema in the browser doesn't automatically update a script you already committed. Commit the schema itself alongside the generated script (as a comment or a separate file) so a future reader can see the source of truth without reverse-engineering it from the generated code. It's also worth matching the draft you select before exporting to whatever the rest of your tooling expects — a script generated against the wrong draft will still run without error, it'll just enforce a subtly different set of rules than you intended (see the draft-07 vs 2019-09 vs 2020-12 post for why that can matter more than it looks).

Frequently asked questions

Is this a VS Code or IDE extension?

No — this is a browser-based tool, not an editor plugin. If you want validation to run as you edit in an IDE, that's a separate integration; what this gives you instead is a generated script for running the same check unattended, in CI or any script-based workflow.

Can I use this with Postman or REST Assured?

Not directly — there's no built-in integration for either. The generated Node or Python script is plain, dependency-light code though, so it can be called from a custom test step in most pipelines that already shell out to scripts.

Does this require a CLI tool to be installed?

No separate CLI — you export a self-contained script that only needs Node (for the ajv snippet) or Python (for the jsonschema snippet) already available in your CI environment, which most pipelines have by default.

What happens if I change the schema after generating the script?

Nothing automatic — the exported script is a snapshot of the schema at export time. Update the schema in the browser, re-run "Copy as snippet," and replace the committed script to keep them in sync.

Does the generated script call back to this website?

No. It's a standalone script using ajv or jsonschema with your schema embedded directly in its source — it has no runtime dependency on this app once generated.

Which draft does the generated script validate against?

Whichever draft is selected in the dropdown when you copy the snippet — draft-07, 2019-09, or 2020-12 — it's baked into the generated script along with the schema itself.
