What is a JSON Schema? A beginner's guide

If you've never heard the term before: a JSON Schema is just a way of writing down "here are the rules this data has to follow" — in plain English first, then we'll show the actual syntax.

Start with JSON itself

JSON (JavaScript Object Notation) is a simple way of writing structured data as text. Here's a tiny example describing a person: 

{
  "name": "Alex",
  "age": 29,
  "email": "alex@example.com"
}

That's it — curly braces hold a set of "key": value pairs. Values can be text (in quotes), numbers, true/false, lists (in square brackets), nested objects, or null. JSON is everywhere: it's how most websites and apps send data back and forth, and how a lot of config files and API responses are written.

The problem JSON alone doesn't solve

JSON only describes that something is structured data — it says nothing about whether the data makes sense. This is also valid JSON: 

{
  "name": 42,
  "age": "banana",
  "email": "not an email at all"
}

A JSON parser will accept that without complaint, because it's syntactically fine — braces match, quotes match, commas are in the right places. But it's obviously wrong data: a name shouldn't be a number, an age shouldn't be the word "banana," and that's not a real email address. JSON on its own has no way to say "age has to be a number" or "email has to look like an email." That's the gap JSON Schema fills.

What a JSON Schema actually looks like

Here's a schema that describes the rules for the "person" example above:

{
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "integer", "minimum": 0 },
    "email": { "type": "string", "format": "email" }
  },
  "required": ["name", "age", "email"]
}

Read it line by line: the whole thing must be an object. It has three expected properties: name must be text (a string), age must be a whole number (integer) that's at least 0, and email must be text shaped like an email address. The required list says all three fields must be present — leaving one out is itself a violation, separate from getting a value's type wrong.

Notice the schema is also written in JSON — it's just a JSON document whose job is to describe the shape of a different JSON document. That's the whole trick: one simple, text-based format used both for the data and for the rules about the data.

What "validating" means, concretely

Validating means taking a piece of data and a schema and checking the data against every rule in the schema. The result is either "this is valid" (every rule was satisfied) or a list of specific problems — for the broken example above, checking it against the schema would report that name should be a string but got a number, age should be an integer but got a string, and email doesn't match the email format. Instead of a human reading the data and eyeballing what's wrong, a program (called a validator) does this mechanically and precisely, every time, exactly the same way.

What about lists and nested data?

Real data is rarely just flat fields — it often has lists of things, or an object inside another object. JSON Schema handles both the same way: describe the inner shape once, then say where it's used. Say our "person" now has a list of hobbies and a nested address: 

{
  "name": "Alex",
  "hobbies": ["chess", "running"],
  "address": { "city": "Austin", "zip": "78701" }
}

The schema for that looks like this:

{
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "hobbies": {
      "type": "array",
      "items": { "type": "string" }
    },
    "address": {
      "type": "object",
      "properties": {
        "city": { "type": "string" },
        "zip": { "type": "string" }
      },
      "required": ["city", "zip"]
    }
  },
  "required": ["name"]
}

For hobbies, "type": "array" says it must be a list, and "items": { "type": "string" } says every entry in that list must be a string — so ["chess", 42] would fail, because 42 isn't a string. For address, the schema just nests another full object description (with its own properties and required) inside the address field — a schema inside a schema, as deep as your actual data goes.

Tightening up text: length and pattern

"type": "string" alone just says "must be text" — it says nothing about how long, or what shape. Two more keywords narrow that down: minLength/maxLength for how many characters, and pattern for a regular expression the whole string must match. 

{
  "type": "string",
  "minLength": 3,
  "maxLength": 20,
  "pattern": "^[a-z0-9_]+$"
}

That schema fragment describes something like a username: at least 3 characters, no more than 20, and only lowercase letters, digits, and underscores — "al" would fail (too short), "Alex-99" would fail (uppercase letter and a hyphen aren't in the allowed character set), and "alex_99" would pass. See this guide for the exact regex dialect pattern uses and the gotchas that trip people up (it's unanchored by default, for one).

Built-in shapes: the format keyword

Rather than hand-writing a regex for every common shape, JSON Schema defines a set of named format values for things that come up constantly: email, date (2024-03-15), date-time (a full ISO 8601 timestamp), uri, uuid, ipv4, and several more. The earlier email example in this post used exactly this: 

{ "type": "string", "format": "email" }

One subtlety worth knowing early: the JSON Schema specification itself only defines what each format means — whether a given validator actually enforces it (rejecting a string that doesn't match) depends on the validator. Some validators treat format as documentation only, by default, until you explicitly enable format checking as a real assertion. This app's validator enables format assertions by default (via a companion library, ajv-formats), so format behaves the way most people expect here — but if you ever see a different tool silently accept a bad email address despite a format: email constraint, this is why: check whether that tool has format assertions turned on.

Narrowing numbers: minimum, maximum, and multiples

Numbers get their own set of range keywords, parallel to the string ones: minimum and maximum for inclusive bounds, exclusiveMinimum/exclusiveMaximum for bounds that don't include the boundary value itself, and multipleOf for "must be a multiple of this number" (useful for things like "quantity must be ordered in increments of 5"). 

{
  "type": "integer",
  "minimum": 0,
  "maximum": 130,
  "multipleOf": 1
}

That describes a plausible human age: a non-negative whole number, capped at a sane upper bound. Using "exclusiveMinimum": 0 instead of "minimum": 0 would mean 0 itself is rejected, not just negative numbers — useful for something like a price that must be strictly positive.

Restricting values to a fixed set: enum and const

Sometimes a field isn't a free-form string or number at all — it's one of a small, fixed set of allowed values. That's what enum is for: 

{
  "type": "string",
  "enum": ["pending", "shipped", "delivered", "cancelled"]
}

Any value not in that list fails, including a value that's merely close (a typo like "shiped" is rejected just as firmly as a completely unrelated value). When there's exactly one allowed value rather than a small set, const is the more direct way to say it — { "const": "v2" } means that field must be exactly the string "v2", nothing else. This comes up a lot as a "discriminator" field distinguishing between different shapes of object, which the anyOf vs oneOf guide covers in more depth.

Combining rules: allOf, anyOf, oneOf, and not

Beyond describing one shape at a time, JSON Schema has four keywords for combining multiple subschemas:

  • allOf — the value must match every listed subschema. Useful for layering independent constraint sets onto the same value (e.g. one subschema for "must be a valid email" and a separate one for "must be at most 100 characters," combined).
  • anyOf — the value must match at least one listed subschema. Good for "this field can be a string, or a number, or an array of strings."
  • oneOf — the value must match exactly one listed subschema; matching two or more is a failure, not a pass. See the dedicated guide for the difference from anyOf and the overlapping-branches bug that trips people up.
  • not — the value must not match the given subschema. Less common day-to-day, but useful for "anything except this specific shape."

Rules that depend on other fields: if / then / else

Sometimes a field's requirements depend on the value of a different field in the same object — a shipping form might only require a "state" field if "country" is "US", for example. JSON Schema's if/then/else keywords express exactly that: 

{
  "type": "object",
  "properties": {
    "country": { "type": "string" },
    "state": { "type": "string" }
  },
  "if": {
    "properties": { "country": { "const": "US" } }
  },
  "then": {
    "required": ["state"]
  }
}

Read it as a sentence: "if country is US, then state becomes required." An object with country: "CA" and no state field passes fine; an object with country: "US" and no state field fails the required check inside then. This is one of the more advanced JSON Schema features — most schemas never need it — but it's worth knowing it exists for the day a flat set of independent field rules genuinely isn't enough.

Common beginner mistakes

  • Forgetting required. Listing a field under properties only describes what it should look like if present — it doesn't make the field mandatory. A field that must always be there needs to be listed in required too.
  • Mixing up integer and number. integer only allows whole numbers (1, 2, -5); number allows decimals too (1.5). Using number for something that should always be a whole number (like a count of items) won't catch 2.5 as invalid.
  • Expecting typos to be caught automatically. By default, JSON Schema doesn't reject extra fields that aren't in properties — a typo'd field name like "emial" is silently ignored rather than flagged, unless the schema explicitly sets "additionalProperties": false.
  • Reaching for oneOf out of habit. It's tempting to use oneOf any time a field could be "this or that," but if the branches can overlap (a value could legitimately match more than one), oneOf will reject it — anyOf is usually the safer default unless you specifically need to enforce exclusivity. See the anyOf vs oneOf guide for a worked example of this exact bug.
  • Assuming format is always enforced. As covered above, whether format actually rejects bad data (versus just documenting intent) depends on the validator's configuration — don't assume a format: email constraint is doing anything until you've confirmed the tool you're using enforces it.

A few terms you'll see used a lot

  • Schema — the JSON document describing the rules (what we built above).
  • Validate / validation — the act of checking a piece of data against a schema.
  • Validator — the program that does the checking (this app uses a widely-used one called ajv).
  • Draft — JSON Schema itself has had a few versions over the years (draft-07, 2019-09, 2020-12) — see this guide if you want the details, but you can safely ignore this at first and use whichever one a tool picks for you.
  • $ref — a way for one schema to reuse a piece of another schema instead of repeating it, covered in this guide once you're past the basics.

Why this matters beyond "neat trick"

Once a schema exists, it becomes useful in more places than just one manual check: it can generate realistic sample data for tests, generate a plain-English field reference non-engineers can read, generate a TypeScript type so your code and your data rules can't silently drift apart, and catch bad data automatically in a CI pipeline before it ever reaches production. All of those build on the exact same schema you'd write by hand for a single check — nothing extra to learn, just more uses for the same file.

Where JSON Schema shows up without you necessarily noticing

Once you know what to look for, JSON Schema turns up in a lot of places that don't advertise it by name. An OpenAPI (formerly "Swagger") spec — the document that describes a REST API's endpoints — uses JSON Schema internally to describe every request and response body; see this guide for exactly how the two relate. A lot of editors and IDEs validate package.json, GitHub Actions workflow files, and other common config formats against a JSON Schema in the background, which is why you sometimes get a red squiggle in a config file before you've even run anything. Form-building libraries can generate an entire UI form directly from a schema. None of this requires learning anything beyond what's already on this page — it's the same handful of keywords, just consumed by different tools for different purposes.

What a validation error message is actually telling you

When something fails validation, the error isn't a vague "invalid data" — it's specific, and learning to read it saves time. A typical error has three parts: a path (which field, e.g. age, or address.zip for something nested), a keyword (which rule was broken — type, required, pattern, minimum, and so on), and a message describing what was expected. "age — type: must be integer" tells you exactly which field, exactly which rule, and exactly what was expected, without needing to re-read the whole schema to figure out what went wrong. If a tool's error message doesn't give you at least the path and the keyword, it's worth checking whether a different validator exposes that detail instead — ajv (used in this app) reports both, plus the actual received value for most keyword types.

A bigger, more realistic example

The examples so far have been small on purpose, to introduce one idea at a time. Here's something closer to real-world data — a blog post object — combining most of what's been covered: 

{
  "title": "What is a JSON Schema?",
  "slug": "what-is-json-schema",
  "tags": ["beginner", "json", "schema"],
  "status": "published",
  "publishedAt": "2026-10-01T09:00:00Z",
  "author": { "name": "Alex", "email": "alex@example.com" },
  "viewCount": 0
}

And a schema describing the rules for it:

{
  "type": "object",
  "properties": {
    "title": { "type": "string", "minLength": 1, "maxLength": 120 },
    "slug": { "type": "string", "pattern": "^[a-z0-9-]+$" },
    "tags": {
      "type": "array",
      "items": { "type": "string" },
      "minItems": 1,
      "uniqueItems": true
    },
    "status": { "type": "string", "enum": ["draft", "published", "archived"] },
    "publishedAt": { "type": "string", "format": "date-time" },
    "author": {
      "type": "object",
      "properties": {
        "name": { "type": "string" },
        "email": { "type": "string", "format": "email" }
      },
      "required": ["name", "email"]
    },
    "viewCount": { "type": "integer", "minimum": 0 }
  },
  "required": ["title", "slug", "status", "author"],
  "additionalProperties": false
}

Every rule here has a reason: minLength/maxLength on title prevent an empty or absurdly long value; pattern on slug keeps it URL-safe; uniqueItems: true on tags (a keyword not covered earlier — it does exactly what it says, rejecting a list with a duplicate entry) stops the same tag being listed twice; minItems: 1 means at least one tag is required, not just that tags must be an array; enum on status keeps it to the three valid states instead of an arbitrary string; publishedAt reuses the date-time format from earlier; author nests the same "object with required fields" pattern already covered; and viewCount can't go negative. Finally, "additionalProperties": false on the top-level object means a field that isn't listed above — a typo, or an old field nobody removed from the schema — is now rejected outright, closing the gap mentioned earlier in "Common beginner mistakes."

A few more keywords worth knowing

  • default — documents what value should be assumed if a field is absent. It's informational for most validators (it doesn't fill the value in for you during validation), but tools that generate sample data or forms from a schema often use it.
  • title and description — pure documentation, attached to any part of a schema. They don't affect validation at all, but they're what a human-readable field-documentation generator (or a hover tooltip in an editor) actually displays.
  • minItems / maxItems — like minLength/maxLength, but for how many entries an array must have.
  • uniqueItems — used in the example above: rejects an array containing a duplicate value.
  • patternProperties — like properties, but the keys are regular expressions instead of exact field names, for objects whose field names aren't known ahead of time but follow a pattern.
  • $defs (or definitions in older drafts) — a place to define reusable subschemas once and reference them elsewhere with $ref, instead of repeating the same shape. See the $ref guide for the full picture, including referencing schemas across separate files.

A brief history, and who maintains JSON Schema

JSON Schema is a community-maintained specification, not something owned by a single company — its home is json-schema.org, where every draft version's full specification is published. It has gone through several draft versions over the years (draft-07, 2019-09, 2020-12 being the most widely used today — see this guide for what actually changed between them), each refining edge cases and adding new capabilities while keeping most existing schemas working unchanged. It's been adopted well beyond its original scope, too: OpenAPI specs embed it directly, AsyncAPI (a similar specification for event-driven/async APIs) uses it for message payloads, and validator implementations exist in essentially every mainstream programming language — this app uses a JavaScript one called ajv, but the same schema document works unmodified against a Python, Java, Go, or Rust validator, because the schema itself is just portable JSON text, not tied to any one language or tool.

Troubleshooting: "my data looks right but it's failing"

A few specific situations account for most of the confusing "this should obviously be valid" moments once you move past the basics:

  • Whitespace or hidden characters. A string that "looks" right in an editor can still have a trailing space or an invisible character that a pattern or enum check fails on — pasting into a validator and reading the exact character count or the raw error is more reliable than eyeballing it.
  • Numbers that are actually strings (or vice versa). JSON distinguishes 42 (a number) from "42" (a string that happens to contain digits) — a schema expecting type: "integer" rejects "42" even though a human reading it would say "that's clearly a number."
  • A draft mismatch. A schema written against one JSON Schema draft occasionally behaves subtly differently under another (the draft differences guide covers the concrete cases) — if a schema behaves unexpectedly, confirming which draft is actually being used is worth checking before assuming the schema itself is wrong.
  • The schema matched, just not the branch you expected. With anyOf/oneOf, data can be technically valid while matching a branch you didn't intend — worth checking which branch actually matched, not just whether validation passed overall.

Frequently asked questions

Do I need to know how to code to use JSON Schema?

No — a schema is just a text file written in JSON, and you can write or test one using only a browser-based tool, no programming required. Using one from inside your own code does require some programming, but writing and checking a schema does not.

Is JSON Schema the same thing as JSON?

No. JSON is a data format (like a sentence). A JSON Schema is a separate document, also written in JSON, that describes what a valid piece of JSON data is allowed to look like (like a grammar rule for that sentence).

What does "validating against a schema" actually mean?

It means checking a piece of data against the rules in a schema and getting back either "this matches" or a list of exactly which rules it broke and where.

Why not just check my data with if-statements in code instead?

You can for a couple of fields, but it gets unwieldy fast for anything with many fields, nested data, or rules that need to apply in more than one place (e.g. the same shape checked in three different services). A schema expresses all the rules once, in one readable file, instead of scattered across if-statements in multiple codebases.

Where are JSON Schemas actually used?

Validating API request/response bodies, checking configuration files, describing the data shapes inside an OpenAPI/Swagger spec, validating form submissions, and as a contract between a frontend and backend team so both sides agree on what a piece of data should look like.

What's the difference between a "type" error and a "required" error?

A type error means the field was present but the wrong kind of value (a string where a number was expected). A required error means the field was missing entirely. They're reported separately because they call for different fixes — one is "the value is wrong," the other is "the field isn't there at all."

Can a JSON Schema validate YAML data too, not just JSON?

Yes — YAML and JSON represent the same underlying data (objects, arrays, strings, numbers, booleans, null), so once YAML is parsed into that data, the exact same schema validates it. See the YAML vs JSON guide for more on the relationship between the two formats.

Is there a size limit on how big a schema can be?

The specification itself doesn't impose one — schemas range from a few lines to thousands, depending on how much data they describe. In practice, very large schemas are usually split across multiple files and joined with $ref rather than written as one giant document, both for readability and so shared pieces (like a common "address" shape) aren't duplicated.

Can I share a schema with someone else, or reuse one from elsewhere?

Yes — a schema is just a plain JSON file, so sharing it is the same as sharing any text file (a link, a gist, a file in your repo). Many public APIs publish their request/response schemas, and some ecosystems (like OpenAPI tooling) let you import an existing spec's schemas directly rather than writing new ones from scratch.

What happens if my schema itself has a mistake in it?

Most validators will tell you the schema itself is invalid (for example, a keyword used in a way the spec doesn't allow) rather than silently misbehaving — though a schema that's syntactically fine but logically wrong (like a oneOf with overlapping branches) can still compile and run, just not do what you intended. That's a semantic mistake, not a syntax one, and it's why reviewing a schema's actual behavior against real example data — not just checking that it loads — matters.

Does every programming language support JSON Schema?

Validator libraries exist for essentially every mainstream language — JavaScript (ajv, used by this app), Python, Java, Go, Rust, C#, Ruby, and more. Since a schema is just portable JSON text, the same schema file works across all of them without modification.
