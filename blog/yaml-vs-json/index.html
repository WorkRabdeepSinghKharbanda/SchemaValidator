YAML vs JSON: when to use which

Neither is "better" in general — they trade off readability against strictness, and the right choice depends on who's editing the file and how often.

What they actually are

JSON and YAML both represent the same underlying data model — objects, arrays, strings, numbers, booleans, null — just with different surface syntax. In fact YAML 1.2 is a strict superset of JSON: any valid JSON document is also valid YAML. The differences that matter in practice are about how each format is typically written and read by humans, not what they can represent.

  3. Compare both versions side by side; optionally validate either against the same JSON Schema to confirm nothing changed meaning.

Where JSON wins

  • Machine-to-machine. JSON is the native wire format of nearly every HTTP API, and every language has a fast, built-in JSON parser. There's no ambiguity in how a JSON document should be parsed.
  • Strictness. JSON's syntax is small and unambiguous — quoting rules, structure, and types are rigid, which makes it a good target when you want exactly one correct way to represent a value.
  • Diffing and tooling. JSON's flat, bracket-delimited structure is easy for generic diff tools and linters to reason about, since whitespace carries no meaning.

Where YAML wins

  • Human-edited config. YAML drops most of JSON's punctuation (quotes around keys, braces, commas) in favor of indentation, which is why it dominates for files people hand-edit often: Kubernetes manifests, GitHub Actions workflows, CI pipelines, Docker Compose files.
  • Comments. YAML supports # comments natively; standard JSON has no comment syntax at all (this repo's own JSON panes work around that by tolerating JSONC-style comments, but that's an extension, not standard JSON).
  • Multiline strings. YAML's block scalars (| and >) make embedding a shell script or a long description readable; the JSON equivalent is one long escaped string on a single line.

Where YAML's flexibility bites you

YAML's permissiveness is also its biggest footgun. Unquoted values are type-inferred — version: 1.0 can silently become a float instead of a string, enabled: yes becomes a boolean in some parsers and a string in others, and indentation errors can change a document's structure without any syntax error being raised at all. JSON doesn't have this class of bug, because there's no implicit type inference and no significant whitespace.

Everyday use cases

  • Writing a Kubernetes Deployment or a GitHub Actions workflow — YAML, because you'll hand-edit it repeatedly and want comments.
  • An API request/response body — JSON, because it's what HTTP clients and servers expect natively.
  • A one-off config file for a small script that only you will touch — either works; pick whichever your config-loading library already supports.
  • Generating config programmatically and never hand-editing it — JSON is simpler to produce correctly, since there's no indentation-sensitivity to get wrong.
  • Documenting an OpenAPI spec for readability — many teams maintain the source as YAML (for comments and multiline descriptions) and generate JSON for tooling that expects it.

Tooling and ecosystem support

Every mainstream language has a JSON parser in its standard library or one dependency away, and the parsing itself is fast and unambiguous — there's exactly one way to read a given JSON document. YAML parsing is more involved: the spec is large (YAML 1.1 and 1.2 even disagree on some edge cases, like whether yes/no are booleans), and different libraries have historically handled those edge cases differently. This is less of a concern today — most modern tooling has converged on YAML 1.2 semantics — but it's part of why JSON remains the safer choice for anything parsed by many different systems you don't all control.

Editor support also differs: JSON's rigid structure makes it easy for an editor to validate against a schema and catch errors as you type (this is exactly what Monaco, the editor this app uses, does for the JSON panes). YAML's significant whitespace makes equivalent tooling harder to get exactly right, though most modern editors handle it reasonably well.

Common mistakes

The most common YAML mistake is assuming a value stays a string just because it looks like text — always quote values that could be misread as a number, boolean, or date (version strings, phone numbers, affirmative/negative words). A close second is inconsistent indentation — mixing tabs and spaces, or losing track of nesting depth in a deeply nested manifest, which can silently change which key a value belongs to without raising a syntax error. The most common JSON mistake, especially when a file was hand-edited or copy-pasted from JavaScript source, is a trailing comma or single-quoted string — both of which a strict JSON parser rejects outright, though this app's JSON panes tolerate both along with comments (JSONC-style), so pasting slightly-off JSON here still works for a quick check.

Frequently asked questions

Is YAML better than JSON?

Neither is categorically better — YAML is friendlier for files people hand-edit often (comments, less punctuation); JSON is simpler and less ambiguous for machine-to-machine data and API payloads.

Can every JSON file be read as YAML?

Yes — YAML 1.2 is a superset of JSON, so any valid JSON document is also valid YAML.

Why did my version number turn into a different value in YAML?

YAML infers types from unquoted values — 1.0 can become a float, losing the trailing zero. Quote any value you need treated as a literal string.

Can I validate both formats with the same JSON Schema?

Yes — both represent the same underlying data model, so one schema covers both. Schema Validator validates either against the identical schema.

Which one should I use for a new Kubernetes or CI config?

YAML — it's the standard for both ecosystems, and you'll benefit from comments and more readable multiline values.
