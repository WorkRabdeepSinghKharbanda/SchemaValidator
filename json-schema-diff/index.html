JSON Schema Diff

See exactly what changed between two versions of a JSON Schema — free, in your browser, as a line diff.

Compare schema versions

Why diff a schema instead of eyeballing two files?

A schema change that looks small in a text editor — a field moved from required, a type widened, a nested object restructured — can have a large effect on what data now passes or fails. A line diff makes exactly what changed obvious at a glance.

This matters most right before a schema change ships somewhere else consumes it — an API contract, a config validator, a data pipeline's intake check. A reviewer skimming two JSON blocks side by side in a pull request easily misses a single added entry in a required array buried among a dozen unchanged properties, even though that one line is the whole behavioral difference: previously-valid data starts failing the moment it ships. A focused line diff turns that into something obvious at a glance instead of something you hope someone notices in review.

How it works

  1. Save a version of your schema as a named workspace in Schema Validator.
  2. Edit the schema further, or load a different version into the schema pane.
  3. Open the schema pane's "⋯" menu → "Compare with" and pick the saved workspace.
  4. A line diff of that workspace's schema vs. the current one renders below the editors.

One important detail: the comparison is always saved workspace vs. whatever is currently in the schema pane, never two saved workspaces against each other directly. To diff two specific past versions, load the older one into the schema pane first (via the Saved drawer), then pick the newer one from "Compare with" — or vice versa, since a line diff reads the same information either direction, just with additions and removals swapped.

For example, saving this as a workspace named v1:

{
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "integer" }
  },
  "required": ["name"]
}

then editing the schema pane to:

{
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "integer", "minimum": 0 },
    "email": { "type": "string", "format": "email" }
  },
  "required": ["name", "age"]
}

and picking v1 from "Compare with" shows a line diff highlighting the new "minimum": 0 constraint, the added email property, and age moving into required — exactly the kind of change that's easy to miss scanning two JSON blocks side by side but obvious in a line diff, and exactly the kind of change ("age is now required") that would start rejecting previously-valid data if you rolled it out without noticing.

Common errors and how to read them

  • "Compare with" dropdown is empty. There are no saved workspaces yet — the diff needs at least one named workspace to compare against. Save your current schema (or an earlier version of it) as a workspace first via the Saved drawer.
  • Diff shows the whole schema as removed and re-added, not a focused change. Usually means formatting changed as much as content — different indentation, key order, or quote style between the saved version and the current one. The diff operates on text lines, not a structural/semantic AST comparison, so reformatting the whole file (even with no real schema change) can produce a noisy diff. Keep formatting consistent between saves if you want diffs to stay focused on actual changes.
  • Diff doesn't reflect a change you just made. The diff panel renders against the schema pane's current text at the moment you open "Compare with" — if you're in Visual builder mode and haven't synced back to Code mode, or the schema pane has an unsaved syntax error, check the Code view actually shows your latest edit before comparing.
  • Expected a data diff, got nothing / wrong panel. This feature only diffs schemas. For data, use "Diff from last valid" instead, which compares the current data pane against the last version that passed validation — a different feature, reachable from the data pane, not the schema pane's menu.

Frequently asked questions

Can I diff two saved workspaces directly?

Not two arbitrary saved schemas against each other — diff compares a saved workspace against whatever is currently in the schema pane, so load one as current first.

Does it diff data too, or just the schema?

Just the schema. For data, use "Diff from last valid", which compares current data against the last version that passed validation.

Is anything uploaded?

No, the diff is computed entirely in your browser.

Is there a JSON Schema compare tool I can use online without saving anything?

The comparison itself always runs against a saved workspace, by design — the diff needs something stable to compare the current schema pane against, and "whatever happened to be in the pane a minute ago" isn't stable. Saving a workspace is a one-click action (name it, done) and nothing leaves your browser, so it's still an entirely local, no-sign-up comparison — just one that needs that one save step first.

What's the difference between anyOf and oneOf in JSON Schema?

Briefly: anyOf passes if the data matches at least one of the listed subschemas (matching more than one is fine), while oneOf requires matching exactly one — matching two or more subschemas fails oneOf even though each individually would have passed. This trips people up most with overlapping subschemas (e.g. a loose {"type": "object"} alongside a stricter one). See the anyOf vs oneOf post for worked examples — it's a separate point of confusion from schema diffing, not something this diff feature itself resolves.

Does the diff understand JSON Schema semantics, like reordered properties meaning no real change?

No — it's a plain line diff (via the diff package) over the schema's text, not a schema-aware structural comparison. Reordering properties keys with no other change will show as a diff even though the schema's meaning is identical. Keep formatting/ordering consistent between saves if that matters to you.

Can I see when a required field was added or removed across versions?

Yes, as long as it shows up as a text change — a field added to or removed from the required array appears as an added/removed line in the diff, same as any other schema change. There's no dedicated "required fields changed" summary separate from the line diff itself.
