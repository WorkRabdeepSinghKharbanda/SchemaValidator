JSON Schema Documentation Generator

Turn a JSON Schema into a readable field-by-field doc — Markdown or a branded PDF table — free, in your browser.

Generate field docs now

Why generate docs from a schema instead of writing them separately?

A schema and a hand-written field-reference doc drift apart the same way a schema and a hand-written TypeScript type do. Someone adds a field to the schema, forgets the doc, and six months later the doc is actively wrong rather than just incomplete. Generating the doc directly from the schema removes that failure mode entirely — the doc can never describe a field that no longer exists, or omit one that was just added, because it's rebuilt from the schema every time you export it.

It also solves a distribution problem. A product manager, support engineer, or external API consumer usually doesn't want the raw schema — nested properties, $ref pointers, additionalProperties: false — they want a table of field names, types, and whether each one is required. That's exactly what this generates.

How it works

  1. Open Schema Validator and paste your JSON Schema into the schema pane.
  2. Use the schema pane's "⋯" menu → "Export field docs".
  3. Choose Markdown (for a repo README or wiki page) or PDF (a branded table, ready to share as-is, no further formatting needed).
  4. Send it to whoever needs a plain-English reference instead of the raw schema.

Given a schema like this:

{
  "type": "object",
  "properties": {
    "id": { "type": "string", "format": "uuid" },
    "email": { "type": "string", "format": "email" },
    "address": {
      "type": "object",
      "properties": {
        "city": { "type": "string" },
        "zip": { "type": "string", "pattern": "^[0-9]{5}$" }
      },
      "required": ["city"]
    },
    "tags": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["id", "email"]
}

the Markdown export produces a flat table — one row per top-level field, and one row per field inside the nested address object (shown as address.city, address.zip) — with its type, required/optional status, and any format/enum/description pulled from the schema. The tags field shows up as a single row of type array; its items shape is not expanded into separate rows (see the FAQ below).

Common gaps and how to read the output

  • An array field shows no column for what's inside it. This is the most common surprise — a tags or items array field appears as one row, type array, with no indication that each entry must itself be a string, object, or number. If the array's items have real structure worth documenting, call it out manually in the schema's description for that field, or open the schema itself alongside the doc.
  • A field documented via $ref won't show its real shape unless the reference is already resolved in the schema pane — the docs generator walks the schema's own properties, not resolved reference schemas. Register the referenced schema first (schema pane's "⋯" menu → reference schemas) if you need the dereferenced shape documented.
  • Missing descriptions show as a bare dash. The "Details" column only has content if the schema itself carries a description, format, or enum — an undocumented field in the schema stays undocumented in the output. Add a description to the schema, not to the generated doc, so it survives the next export.
  • A field with a non-trivial required array for a nested object is read correctly — the "Required" column for address.city reflects address's own required list, not the root schema's.

Typical use case

A common flow: write the schema once as the source of truth for an internal API payload or a config file format, then export field docs whenever a new team member or external integrator needs a reference — instead of maintaining a separate hand-written spec that silently falls out of sync the first time someone adds a field under deadline pressure.

Another common case: a support team fielding "what does this field mean" tickets about a webhook payload or config file, where the engineering team already has the schema but nobody's translated it into something a non-engineer can skim. Exporting field docs once and dropping the Markdown into an internal wiki page closes that gap without anyone hand-maintaining a second document.

Markdown vs. PDF: which to pick

Both exports cover the same table — the choice is about where it's going, not what it contains. Markdown fits a GitHub/GitLab repo README, an internal wiki page, or anywhere else that already renders Markdown natively; it's plain text, so it diffs cleanly in version control and can be edited further by hand. The PDF export is for anywhere a polished, finished document is expected — an email attachment to an external partner, a spec handed to a vendor, or anywhere Markdown's raw syntax would look unfinished. The PDF carries the app's own dark branding (header band, diamond mark, consistent footer) rather than a generic default-styled table, so it reads as a deliberate deliverable rather than a debug dump.

Keeping docs in sync over time

Because the doc is generated, not maintained, "keeping it in sync" is really just "re-export after a schema change" rather than a separate editing task. A practical habit: re-export field docs as part of whatever process already updates the schema itself (a PR that changes the schema, a release checklist) rather than waiting until someone notices the doc is stale. Since the export is a single menu action, this costs seconds, not a dedicated step in a larger process.

Frequently asked questions

Does the PDF look like a plain generic report?

No — it shares the app's own dark theme and brand mark, not a plain white default PDF layout.

Does this replace the Markdown export?

No, both exist side by side — pick whichever fits where you're sharing it.

Does it cover nested fields?

Yes, the field table walks into nested object properties, shown with a dotted prefix like address.city.

Does it break down what's inside an array field?

No — an array field is documented as a single row of type array. The schema for its items is not expanded into its own rows. If the array items are themselves objects with meaningful structure, document that structure in the field's description or keep the schema itself nearby.

Does it resolve $ref pointers to external or reference schemas?

It documents the schema as written. A $ref to a reference schema registered in the app's reference-schema panel isn't dereferenced into the output table — document the referenced schema separately, or inline it before exporting if you need one combined table.

Can I generate docs for just part of a large schema?

Not directly — export covers the whole schema currently in the schema pane. For a subset, paste just that fragment (as its own valid schema object) into the schema pane before exporting.

Does this work for OpenAPI-derived schemas?

Yes — import an OpenAPI/Swagger spec's component schemas (via the OpenAPI import panel) and export docs for any one of them the same way.
