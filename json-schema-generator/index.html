Why generate a schema instead of writing one by hand?

Writing a JSON Schema from scratch for an existing API response or config file means re-typing every field, type, and nesting level you can already see in the data. Schema inference reads your actual sample data and produces a starting schema in seconds, that you refine rather than write from zero. It's also a faster way to get a second opinion on a schema's shape — infer one from a known-good example and diff it against what you already wrote to spot a field you forgot to constrain.

How it works

  1. Open Schema Validator and paste sample JSON data into the data pane.
  2. Use the schema pane's "⋯" menu → "Infer schema from data".
  3. A draft schema is written into the schema pane, matching the data's types and nesting.
  4. Refine it — add required fields, tighten an enum, or switch to the Visual builder.

For example, given this sample data:

{
  "id": "a1b2c3",
  "active": true,
  "price": 19.99,
  "tags": ["sale", "clearance"],
  "shipping": {
    "method": "standard",
    "cost": 4.5
  }
}

inference produces:

{
  "type": "object",
  "properties": {
    "id": { "type": "string" },
    "active": { "type": "boolean" },
    "price": { "type": "number" },
    "tags": { "type": "array", "items": { "type": "string" } },
    "shipping": {
      "type": "object",
      "properties": {
        "method": { "type": "string" },
        "cost": { "type": "number" }
      },
      "required": ["method", "cost"]
    }
  },
  "required": ["id", "active", "price", "tags", "shipping"]
}

Note that every top-level key present in the sample ends up in required — the inference has no way to know which fields are optional from a single example, so it treats everything it sees as required. This is a reasonable starting point, not a final answer: go through the inferred schema and remove any field from required that won't always be present in real data.

Working with nested and complex sample data

Object nesting infers correctly to any depth — a shipping.address.country three levels deep produces three levels of nested properties in the output, matching the "Visual schema builder" feature's own depth handling. Arrays are where inference is deliberately limited: an array's shape comes from its first element only. If your sample array looks like [{"type": "email"}, {"type": "sms", "retries": 3}], the generated items schema is built purely from the first object — the retries field on the second element won't appear anywhere in the output schema, since it was never shown the second element.

In practice this means: if an array in your sample data mixes shapes (some objects have an extra optional field, some don't), either pick a sample element that has every field you want represented, or manually add the missing fields into the schema pane after inferring. A field that only exists on a later array element is the single most common gap to check for after inferring from real-world data.

Troubleshooting

  • Everything came back required and that's not what I want. Expected — see above. Manually edit the required array (or use the Visual builder, which lets you toggle a field's required status without touching raw JSON).
  • An array field's items look too narrow. You're seeing the first-element-only limitation. Re-order your sample so the most "complete" object is first, or hand-edit items.properties afterward.
  • A numeric field came back as integer when I wanted number. Inference checks Number.isInteger() on the sample value — if your example happened to be a whole number (e.g. 5 instead of 5.0), it infers integer. Change it to number in the schema pane if the field should actually accept decimals.
  • A null value in the sample produced {"type": "null"}. That's a literal reading of the sample — if the real field is nullable-or-string rather than always null, change the type by hand (e.g. {"type": ["string", "null"]}).

Use case: inferring a schema from an existing API response

A common entry point: you're integrating against a third-party API that has no published schema, only example responses in its docs. Paste one real response into the data pane, infer a schema from it, then tighten it by hand — add enum constraints for fields you know only take specific values, loosen required for fields the docs say are optional, and add a format hint (date-time, email, uri) for fields that are more specific than a bare string. This gets you a working validation schema in minutes rather than hand-transcribing every field from documentation.

From inferred schema to working validator

An inferred schema is immediately usable — it's a normal schema in the schema pane, so the next natural step is usually to validate more sample data against it right away to see if the inferred shape actually generalizes. If a second real example fails validation against the schema inferred from the first, that's useful signal: either tighten the schema further, or loosen a field (drop it from required, broaden a type to an array of types) to match what real data actually looks like across more than one example. Treat the first inference as a hypothesis about the data's shape, confirmed or corrected by validating against further samples — not a final schema from a single example.

Frequently asked questions

Does it infer nested objects and arrays?

Yes, for object nesting. Arrays infer their shape from the first element only — a documented limitation, not a bug — so review array item schemas if your array has mixed shapes.

Is my sample data uploaded anywhere?

No — inference runs entirely in your browser.

Can I edit the generated schema afterward?

Yes, it's a normal editable schema in the schema pane — refine it in Code mode or the Visual builder like any other schema.

Does this generate a UI form from my schema?

No — this goes the other direction, inferring a schema from data. It doesn't render an input form from a schema.

Can I pick which JSON Schema draft the output targets?

Yes — the draft dropdown (draft-07, 2019-09, 2020-12) applies to the whole app, including inferred schemas.

Why does the inferred schema mark every field as required?

Because inference only ever sees one example — it has no way to know which fields might be absent in other real records, so it treats every key it saw as required. Remove fields from required by hand for anything that's genuinely optional.

Can it infer a schema from a complex, deeply nested payload?

Yes for object nesting, to any depth — each nested object becomes its own nested properties block. The first-element-only limitation applies only to arrays, not nested objects.
