JSON Schema Linter

Catch common JSON Schema smells — before they cause a confusing validation bug — free, in your browser.

Lint your schema now

Why lint a schema, if it already validates fine?

A schema can be syntactically valid and still have real problems: a required field that's never declared in properties (which can never pass), an unset additionalProperties that silently accepts typo'd field names, or a single-value enum that should just be a const. These aren't validation errors — ajv has nothing to complain about, because the schema is perfectly legal JSON Schema. They're the kind of mistake that only shows up later, as a confusing bug report from someone whose typo'd field was silently accepted, or a required field nobody can ever satisfy.

How it works

  1. Open Schema Validator and paste your JSON Schema.
  2. Below the schema summary, expand the "Schema lint hints" section.
  3. Review each hint — unset additionalProperties, undeclared required fields, single-value enums.
  4. Fix what applies; hints are suggestions, not hard errors.

The three checks, with examples

1. Unset additionalProperties on an object schema. By default, JSON Schema objects accept any extra property not listed in properties — this is correct behavior per spec, but it's rarely what someone means when they write a schema meant to describe an exact shape. Given:

{
  "type": "object",
  "properties": {
    "email": { "type": "string", "format": "email" }
  }
}

a payload like { "emial": "a@b.com" } validates successfully — the typo'd key is just an "extra" property, and no email was ever required, so there's nothing to fail on. The linter flags this schema with an info hint rather than guessing whether you meant additionalProperties: false, a patternProperties rule, or genuinely wanted an open shape — it only tells you the field is unset, not what to set it to. (If patternProperties is already present, the linter treats that as an intentional, already-handled case and stays quiet.)

2. A required entry not declared in properties. This one is a warn-severity hint because it's an authoring mistake with no good-faith interpretation — usually a field that was renamed in properties without updating required to match, or a copy-paste from a different schema version:

{
  "type": "object",
  "properties": {
    "name": { "type": "string" }
  },
  "required": ["name", "email"]
}

Here email is required but was never declared as a property. The fix is almost always to either add the missing property definition or remove the stale entry from required — the linter doesn't pick for you.

3. A single-value enum. "enum": ["active"] says the same thing as "const": "active", but less clearly — const communicates "this value is fixed" at a glance, where a one-item enum reads like it might grow a second value later (and often it should, in which case the hint is a nudge to go add it, not just rename the keyword).

Common patterns the linter deliberately doesn't flag

If you're expecting more coverage than the three checks above, here's what's intentionally out of scope: pattern/format guessing (e.g. a string field named email with no format: "email" set — the linter won't infer intent from a field name), missing description/title annotations, numeric range sanity checks (minimum greater than maximum, which ajv itself would reject at compile time anyway), and anything involving $ref resolution — a schema node with $ref is skipped entirely rather than resolved, so lint hints never apply to the referenced schema's own shape from the referencing side.

Common errors and how to read them

"additionalProperties isn't set on root — any extra field will silently pass validation." This is the hint on the top-level schema itself (empty path renders as "root"). If your schema describes an API request body you control end-to-end, set additionalProperties: false and re-check — if a legitimate field now gets rejected, it was missing from properties, which the linter would separately have caught if it were also listed in required.

A hint path like address.zip. Hints on nested objects show a dotted path built from the property chain, and array items get a [] segment — e.g. items[].sku for an unset additionalProperties three levels into an array-of-objects schema. The recursion is depth-capped at 6 levels; a schema nested deeper than that stops producing hints past the cap rather than recursing indefinitely.

No hints shown at all. Either the schema is genuinely clean by these three checks, or it's a non-object top-level schema (a bare {"type": "string"} schema has no properties to check) — the "Schema lint hints" section only has something to show for object-shaped schemas with nested structure.

When this matters most

The unset-additionalProperties check earns its keep most on schemas validating external input — a webhook payload, a form submission, an imported CSV row — where a typo'd key silently passing is worse than it sounds: it means the real field (which is required) is also missing, but if it's not marked required either, the whole record passes with neither the typo'd nor the correct key ever checked. Running the linter right after writing a new schema, before it's used against real traffic, catches this class of bug while it's still a one-line fix instead of a production incident.

Frequently asked questions

Does linting replace validation?

No — it's a separate, best-practice pass alongside normal ajv validation, not a substitute for it. A schema can pass every lint check and still reject bad data, or fail every lint check and still validate data correctly; they're answering different questions.

Does it check nested schemas?

Yes, recursing into nested properties and array items (depth-capped at 6 levels), skipping $ref nodes rather than guessing at what they resolve to.

Can a lint hint ever be wrong?

The checks are deliberately conservative — only flagging things that are unambiguously worth a second look, not guessing at intent. There's no pattern/format heuristic guessing (e.g. assuming a field named "email" should have format: "email") — only checks that hold regardless of what the schema author actually meant.

Does the linter check $ref targets?

No — a node with $ref is skipped entirely rather than resolved against an uploaded reference schema. If you want the referenced schema itself linted, paste it into the schema pane directly (or as the main schema, if it's the one you're authoring).

What's the difference between the "info" and "warn" severities?

warn is reserved for the undeclared-required-field case, since that schema can genuinely never be satisfied by any instance for that field. additionalProperties and single-value enum are info — stylistic/defensive suggestions, not logical impossibilities.

Does it flag missing minimum/maximum or format keywords?

No — only the three checks described above. Numeric range and format-correctness issues are either caught by ajv itself at validation time or are too intent-dependent to flag without guessing.

Can I lint a schema that uses allOf/oneOf/anyOf?

The linter walks properties and array items specifically — branches under allOf/oneOf/anyOf aren't separately recursed into in this version, so hints inside those branches won't surface. Lint the branch schemas individually if you need coverage there.
