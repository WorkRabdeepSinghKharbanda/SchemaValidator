JSON Schema to TypeScript

Turn a JSON Schema into a TypeScript interface — free, in your browser, no build step required.

Export a TypeScript interface

Why generate types from a schema instead of hand-typing them?

A JSON Schema and a hand-written TypeScript interface for the same data drift apart the moment either one changes. Generating the interface directly from the schema keeps them in lockstep — paste the schema once, get the type, and regenerate whenever the schema updates.

How it works

  1. Open Schema Validator and paste your JSON Schema.
  2. Use the schema pane's "⋯" menu → "Export as TypeScript interface".
  3. A .d.ts-style interface is generated, with nested objects broken out into their own named interfaces.
  4. Copy it into your codebase.

What the generated output actually looks like

Given this schema:

{
  "type": "object",
  "properties": {
    "id": { "type": "string" },
    "role": { "enum": ["admin", "member"] },
    "address": {
      "type": "object",
      "properties": {
        "city": { "type": "string" },
        "zip": { "type": "string" }
      },
      "required": ["city"]
    }
  },
  "required": ["id", "address"]
}

the generator produces two interfaces — the nested address object gets its own name, declared above the interface that references it, and a field not listed in required becomes optional (?):

export interface Schema_addressNested0 {
  "city": string;
  "zip"?: string;
}

export interface Schema {
  "id": string;
  "role"?: "admin" | "member";
  "address": Schema_addressNested0;
}

Nested interface names follow a predictable {ParentName}_{fieldName}Nested{N} pattern — so Schema_addressNested0 reads as "the nested object under Schema's address field," not a naming bug or leftover placeholder.

How specific keywords map to TypeScript

  • "type": "integer" and "type": "number" both become TypeScript's number — TypeScript has no separate integer type, so this isn't a loss of information the generator could fix.
  • enum becomes a union of literal types ("admin" | "member"), not a TypeScript enum construct — this matches how most codebases consume JSON Schema enums as literal unions rather than native TS enums.
  • oneOf and anyOf are both rendered as a union (|) of their branch types — TypeScript doesn't distinguish "exactly one of" from "any of" the way JSON Schema does, so both collapse to the same union syntax.
  • $ref becomes a bare type reference using only the final path segment of the pointer — "$ref": "#/components/schemas/Address" becomes the type name Address, not an inlined copy of that schema's shape.
  • allOf, if/then/else conditionals, and tuple-style items (an array of per-position schemas rather than one schema for every item) all fall back to unknown — these don't have a clean, unambiguous TypeScript equivalent the generator is willing to guess at.

Common errors and how to read them

Every field comes out as unknown. Check that you pasted a JSON Schema, not a raw JSON data sample — a plain data object like {"id": "abc"} has no type/properties keywords for the generator to read, so it falls through to the catch-all. Run it through the schema generator first if all you have is example data.

A referenced type name doesn't exist anywhere in the output. $ref targets aren't resolved or inlined — if your schema references #/definitions/Address but Address isn't defined elsewhere in your own codebase, you'll need to either generate that referenced schema separately and merge the interfaces by hand, or inline the full schema in place of the $ref before exporting.

A field you expected to be optional isn't, or vice versa. Optionality is read directly from the schema's required array at each nesting level — a property's own schema has no bearing on whether it's optional; only whether its name appears in the parent's required list does.

Nested interface names look auto-generated and ugly. They are — {Name}Nested{N} is deliberately mechanical rather than guessing a nicer name from context. Rename them by hand after pasting into your codebase if the generated names aren't descriptive enough for your use.

When this is (and isn't) the right tool

This is a good fit when a JSON Schema is already your source of truth — an API contract, a config file schema, a validated webhook payload — and you want the matching TypeScript shape without maintaining two documents by hand. It's not a substitute for an OpenAPI-to-TypeScript code generation pipeline if you need request/response types for an entire API surface with many operations; for that, OpenAPI's components.schemas can be pulled into this tool via the schema pane's OpenAPI import feature one schema at a time, but there's no batch "generate every type in this spec" mode here.

Frequently asked questions

Does it handle every JSON Schema keyword?

It's best-effort: type, properties, required, items, enum, $ref, and oneOf/anyOf (as unions) are supported; more complex constructs like allOf or conditionals fall back to unknown.

What happens to nested objects?

Each becomes its own named interface, generated above the interface that references it, following a {ParentName}_{fieldName}Nested{N} naming pattern.

Does $ref get resolved against my reference schemas?

No — a $ref is rendered by its final path segment as a type name, not resolved/inlined. If the referenced type isn't declared elsewhere in your codebase, you'll need to add it yourself.

Does this convert raw JSON data to TypeScript, or a JSON Schema?

A JSON Schema — paste the schema, not a sample data file. If you only have example data, use the schema generator first to infer a schema from it, then export that schema as TypeScript here.

Does it generate a class, or an interface?

An interface declaration (.d.ts-style), not a class — there's no constructor or methods, just the shape of the data.

What about a "model" or "type" instead of an interface?

Not generated separately — the output is always an export interface declaration. A TypeScript type alias and an interface are interchangeable for describing an object shape like this one, so pasting the generated interface and changing the keyword to type plus = works if your codebase's convention prefers that.

How does integer vs number get typed?

Both become TypeScript's number — TypeScript has no separate integer type, so this distinction from JSON Schema doesn't carry over.

What happens with tuple-style arrays (a fixed sequence of different types per position)?

Falls back to unknown — the generator handles the common case of "array of one item type" (items as a single schema) but not the tuple form where items is itself an array of per-position schemas.
