JSON Validator

Check JSON syntax, or validate JSON data against a JSON Schema — free, in your browser, with exact line-number error markers.

Validate your JSON now

Syntax check or schema validation — your choice

Paste JSON with an empty schema pane and get a plain syntax check: is this valid JSON, and if not, exactly which line broke it. Add a JSON Schema and the same data gets checked against required fields, types, patterns, and every other constraint the schema declares. Nothing you paste is uploaded — parsing with jsonc-parser and schema checking with ajv both run in your browser.

How it works

  1. Open Schema Validator — the JSON tab is selected by default.
  2. Paste or upload your JSON data.
  3. Optionally paste a JSON Schema (draft-07, 2019-09, or 2020-12 — the dropdown auto-detects the draft from a $schema field if your schema has one) to validate structure, not just syntax.
  4. Errors show inline at the exact line, each with a plain-English explanation and, for common mistakes, a one-click fix.

A minimal example — schema and data that fails it: 

// schema
{
  "type": "object",
  "required": ["id", "email"],
  "properties": {
    "id": { "type": "integer" },
    "email": { "type": "string", "format": "email" }
  }
}

// data — fails: id is a string, email is missing
{
  "id": "4821"
}

Validating this pair reports two errors: /id should be integer (with a one-click "Convert to integer" fix, since "4821" is unambiguously numeric), and email is a required property (with a "Make optional" fix if you'd rather loosen the schema than add the field). Both quick-fixes are specific to the keyword that failed — a pattern mismatch instead gets an inline regex tester against the schema's actual pattern, rather than either of those two buttons.

Common errors and how to read them

Most JSON syntax errors fall into a handful of repeat offenders. Here's what each looks like and how to fix it:

  • Trailing comma before a closing brace/bracket — { "a": 1, }. Strict JSON.parse rejects this; this validator's JSONC leniency accepts it in both panes, so you'll only see this as an error if your target system (an API, a config loader) uses a stricter parser than this tool does — worth testing with a plain syntax check (empty schema pane) first if you're unsure whether your downstream consumer is JSONC-tolerant too.
  • Missing comma between properties — { "a": 1 "b": 2 }. This one JSONC can't forgive; it's a genuine syntax error and gets an exact line/column marker pointing at the token right after the missing comma.
  • Unescaped quote inside a string — { "name": "Say "hi"" }. The parser reports the error at the second unescaped ", which is usually a few characters earlier than where the mistake actually is (the missing \") — check the preceding few characters, not just the reported column.
  • Type mismatch against the schema — schema says "type": "integer", data has "4821" (a string). This is a schema-validation error, not a syntax error — the JSON itself is valid, it just doesn't match the shape the schema requires. These get the "Convert to {type}" quick-fix when the value is unambiguous.
  • Duplicate keys — { "id": 1, "id": 2 }. Both this parser and strict JSON agree here: it's not a syntax error, but only the last value survives, silently. If you're debugging data that "looks right" in the schema pane but validates unexpectedly, search for a duplicate key before assuming the schema itself is wrong.

Use cases

Beyond ad-hoc "is this JSON valid" checks, people use this for: validating an API response body against its documented schema before debugging a client-side bug; checking a config file (a build tool's JSON config, a package.json-style manifest) against a schema before committing it; validating webhook payloads from a third-party service against the shape their docs promise; and generating a quick regression fixture by pasting a known-good payload and using "Generate sample" to produce variations that should still pass.

Frequently asked questions

Syntax only, or schema too?

Both — an empty schema pane means syntax-only; add a schema to also validate structure.

Do I get exact line numbers?

Yes, JSON is the one format with exact line/column error markers.

Comments and trailing commas allowed?

Yes, both panes tolerate JSONC-style comments and trailing commas.

Can I use this JSON validator inside VS Code, Notepad++, Postman, or REST Assured?

No — this is a browser app, not an IDE plugin or test-framework integration. If you need the same check inside a script, test suite, or CI pipeline, use the schema pane's "⋯" menu to copy a self-contained Node.js or Python snippet that runs an equivalent ajv (or jsonschema) check outside the browser, including from inside a REST Assured or Postman pre-request/test script that can shell out to it.

Does this tool fix broken JSON, not just report errors?

For a plain parse error (not a schema mismatch), yes — an "Auto-fix" button wraps jsonrepair to repair common mistakes (missing quotes, trailing commas, unquoted keys) in one click. For a deeper look at JSON repair specifically, see the JSON repair tool page.

Can my schema use $ref to point at another schema file?

Yes — upload reference schemas from the schema pane's "⋯" menu and they're registered before compilation, so a main schema's $ref can resolve against them by the id you give each one.

Which JSON Schema drafts does this support?

Draft-07, 2019-09, and 2020-12, selectable from a dropdown — or auto-detected from the schema's $schema field if it has one.

Can I validate a JSON array where every item must match a schema?

Yes, in two ways: a top-level "type": "array" schema with an items keyword validates the whole array as one document, or turn on batch mode to validate each array element independently and get a pass/fail table — useful when you want to know exactly which records in a large dataset fail, not just that "something" in the array does.

Working with a different format? Schema Validator also supports YAML, CSV, TOML, and XML against the same schema.
