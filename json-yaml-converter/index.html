JSON ⇄ YAML Converter

Convert data between JSON, YAML, TOML, XML, and CSV — free, in your browser, with an optional schema check on the result.

Convert your data now

Why convert formats in the same tool you validate with?

Converting JSON to YAML (or any of the five supported formats to any other) is easy to get subtly wrong by hand — quoting, indentation, or a type that doesn't round-trip cleanly. Converting in the same editor you validate in means you can immediately check the converted output against your schema, not just eyeball it.

How it works

  1. Open Schema Validator and paste your data in its current format.
  2. Use the data pane's format tabs to switch to the target format — this reserializes the data.
  3. Optionally paste a JSON Schema to validate the converted result matches expectations.
  4. Copy or export the converted data.

What the conversion actually does, step by step

This isn't a text transform — it's a parse into an in-memory JavaScript value, followed by a re-serialize into the target format. Given this JSON:

{
  "name": "Ada Lovelace",
  "roles": ["engineer", "writer"],
  "active": true
}

switching to the YAML tab produces:

name: Ada Lovelace
roles:
  - engineer
  - writer
active: true

Because the intermediate form is a plain JS object/array tree, types survive the round trip correctly — true stays a YAML boolean, not the string "true"; a number stays a number. This is the same reason converting JSON → YAML → JSON again reproduces the original data: both directions go through the identical parse/serialize pair, so nothing is lost that either format can represent.

Format-specific quirks worth knowing

  • TOML expects a table (object) at the root. A top-level JSON array or bare scalar has no TOML equivalent at the document root — TOML documents are always key-value tables. Wrap an array in an object first ({"items": [...]}) if you need to target TOML.
  • CSV expects an array of flat-ish records. A single JSON object gets wrapped into a one-row CSV automatically; a deeply nested object inside a record (an object or array as a field value) gets flattened into a single cell's worth of text rather than spread across columns — CSV has no native concept of nesting.
  • XML needs a value fast-xml-parser can represent as elements. A top-level array converts awkwardly to XML (no single root element) — wrapping in an object with one root key, same as TOML, gives a cleaner result.
  • YAML and JSON are the closest pair. Every JSON document is representable in YAML with no loss (YAML is a superset in practice for data this tool handles) — this is the cleanest conversion of the five.

Common errors and how to read them

Converting to TOML silently reorganizes your data, or fails. Check whether your top-level value is an object — if your JSON starts with [ (an array) or a bare string/number, that's the mismatch described above; wrap it in an object with a named key first.

CSV output has one column full of [object Object]-style text or escaped JSON. That's a nested object or array inside one of your records — CSV has no columns for nested structure, so the value is serialized to a flat string instead of being split into more columns. If you need each nested field as its own column, flatten the structure in the source data before converting, or accept the flattened cell if it's only being used for a quick export.

The converted output fails schema validation, but the original data passed. This usually means the schema was written against one specific format's quirks — e.g. a schema expecting a numeric string because the source was always CSV (where every value parses as a string) now sees an actual YAML number instead. Converting between formats can change a value's inferred type even when the value "looks" the same; validate the schema's type keywords match what the new format's parser actually produces.

Switching format tabs with an empty or unparsable data pane does nothing visible. The conversion needs a successfully parsed source first — fix any parse error shown in the current format's tab before switching, or the target tab has no new data to show.

A typical use case

A common flow: an API returns JSON, but the config file it's feeding into is YAML (Kubernetes manifests, GitHub Actions workflows, most infra-as-code tooling). Paste the JSON response, switch the format tab to YAML, and the result is ready to paste into the target file — with an optional schema check in between to confirm the shape didn't quietly change along the way.

Frequently asked questions

Which formats are supported?

JSON, YAML, TOML, XML, and CSV — convert between any pair.

Does conversion ever lose data?

Only where the target format genuinely can't represent the source shape (e.g. deeply nested data flattened into CSV, or an array at the TOML document root) — for JSON/YAML round-trips this is not an issue.

Is my data uploaded anywhere?

No, conversion runs entirely in the browser.

Can I convert a top-level array to TOML?

Not directly — TOML documents are tables at the root, so a bare array has no document-level representation. Wrap it in an object first, e.g. {"items": [...]}.

What happens to nested objects when converting to CSV?

They're flattened into a single cell's worth of text rather than split across columns — CSV has no native nesting concept. If you need per-field columns, flatten the source structure before converting.

Does the converter run a CLI or need an install?

No — it's a browser-only feature of this SPA, no CLI or package install. If you need format conversion in a script or CI pipeline, the schema pane's "Copy as Node.js/Python snippet" feature covers re-running a validation check outside the browser, though it doesn't cover conversion specifically.

Can I validate the converted output against a schema in the same step?

Yes — paste a JSON Schema in the schema pane before or after converting; validation runs against whatever format the data pane's active tab currently shows.

Is YAML better than JSON?

That's a format-choice question, not a conversion one — see YAML vs JSON: when to use which for the comparison. This page covers converting between the two mechanically, not which to pick for a new project.
