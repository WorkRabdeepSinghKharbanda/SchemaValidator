OpenAPI Schema Validator

Import an OpenAPI or Swagger spec, pick any component schema, and validate real request/response payloads against it — free, in your browser, no server round-trip.

Import a spec now

Why validate against an OpenAPI component schema?

An OpenAPI spec describes dozens of request/response shapes, but testing whether an actual payload matches one of them usually means spinning up the API or writing a throwaway script. Schema Validator lets you pull any components.schemas or definitions entry straight out of the spec and validate sample data against it immediately — useful for checking a mock response, a test fixture, or a payload a teammate pasted into a bug report before you trust it matches the contract the spec promises.

A few concrete use cases this covers: confirming a third-party API's actual response matches what its own published spec claims (a real and common source of integration bugs — the spec and the implementation drift apart over time); checking a request body you're about to send against the endpoint's declared schema before debugging a 400 response the hard way; and verifying a mock/fixture file used in tests still matches the contract after the spec itself was updated, without re-running the whole test suite just to catch a shape mismatch.

How it works

  1. Open Schema Validator and use the schema pane's "⋯" menu → Import from OpenAPI/Swagger.
  2. Upload your spec file (JSON or YAML — both are tried automatically, since specs ship as either).
  3. Pick the schema you want from the list of detected component schemas.
  4. That schema loads into the schema pane, and every sibling schema is auto-added as a reference so internal $refs resolve correctly.
  5. Paste sample request/response data and validate as usual.

The import step does real work under the hood: internal refs like "$ref": "#/components/schemas/Address" get rewritten to a plain reference name ("Address"), and every other schema in the spec is registered so that rewritten ref resolves at validate time. For example, importing a spec with: 

{
  "components": {
    "schemas": {
      "User": {
        "type": "object",
        "properties": {
          "name": { "type": "string" },
          "address": { "$ref": "#/components/schemas/Address" }
        },
        "required": ["name", "address"]
      },
      "Address": {
        "type": "object",
        "properties": {
          "city": { "type": "string" },
          "zip": { "type": "string", "pattern": "^[0-9]{5}$" }
        },
        "required": ["city", "zip"]
      }
    }
  }
}

and picking User loads that schema into the schema pane with Address auto-added as a reference schema — so validating {"name": "Dana", "address": {"city": "Austin", "zip": "ABCDE"}} correctly fails on the zip pattern, without you having to manually copy Address anywhere.

Common errors and how to read them

  • "Unresolved ref" warning after import. The spec has a $ref pointing outside components/schemas (or definitions for Swagger 2) — commonly a parameters or responses ref, or a ref into an external file. These can't be rewritten automatically; the panel lists them instead of letting validation fail silently later with a confusing "schema not found" error from ajv.
  • Validation fails with "can't resolve reference" even though the spec looked fine. Usually means the schema you picked references another schema that failed the unresolved-ref check above, or the spec used a non-standard ref path that doesn't match the expected #/components/schemas/Name / #/definitions/Name shape.
  • Import panel says it couldn't parse the file. The importer tries JSON first, then YAML. If both fail, the file usually isn't a valid OpenAPI/Swagger document at all — check for a stray top-level array instead of an object, or a .yaml file that's actually tab-indented (invalid YAML).
  • A Swagger 2.0 spec's schemas don't show up. Swagger 2.0 keeps its schemas under top-level definitions, not components.schemas — if the importer finds neither, double check the spec actually declares swagger: "2.0" or an openapi version field; a spec missing both won't be auto-detected correctly.

Frequently asked questions

Can I validate data against a schema from my OpenAPI spec?

Yes — import the spec, pick a component schema, and it's loaded into the schema pane with its sibling refs resolved.

Does it handle $ref between schemas in my spec?

Yes, for refs inside components/schemas or definitions. Refs to parameters, responses, or external files are flagged as unresolved instead of failing silently.

Is my spec uploaded anywhere?

No — everything runs client-side. Nothing is sent to a server.

Which OpenAPI/Swagger versions does this support?

OpenAPI 3.0 and 3.1 (components.schemas) and Swagger 2.0 (definitions) — both are detected automatically from the spec's structure.

Can I import an OpenAPI 3.1 spec specifically, not just 3.0?

Yes — the importer reads components.schemas the same way for 3.0 and 3.1, since the schema object shape didn't change between them for this purpose. Once imported, pick the draft matching what the spec's schemas were authored against (3.1 schemas are closer to 2020-12 JSON Schema; 3.0 schemas are closer to draft-07 with some restrictions) in the toolbar's draft dropdown for the strictest match.

What happens to refs pointing at parameters or responses, not schemas?

Those aren't rewritten or auto-resolved — extractOpenApiSchemas() only handles refs inside components/schemas (or definitions). A ref to components/parameters, components/responses, or an external file is reported back as an unresolved ref so you know about the gap rather than hitting a silent ajv compile failure later.

Can I validate request parameters or headers, not just request/response bodies?

Only if they're expressed as a schema under components.schemas/definitions and you pick it directly — parameter and header definitions that live under components.parameters or inline in a path item aren't extracted as pickable schemas by the importer today.

Does this replace a full OpenAPI contract-testing tool?

No — it validates one payload against one chosen schema from the spec, on demand, in the browser. It doesn't run your whole test suite against every path/method/response-code combination in a spec, and doesn't spin up a mock server. For that scope, you'd still want a dedicated contract-testing setup; this tool is for a quick one-off check.
