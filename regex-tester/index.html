Regex Tester for JSON Schema Patterns

See exactly why a pattern validation error fired, and test a fix live — free, in your browser.

Test a pattern now

Why test a regex inside the validator instead of a separate regex tool?

A pattern-keyword validation error tells you a value didn't match, but not why — testing the actual schema pattern against candidate values in a separate regex tool means re-copying the pattern by hand and hoping you copied it exactly, with no quotes, escapes, or anchors dropped in transit. Testing it inline, against the same pattern string ajv just used, removes that step: the pattern is pulled straight from the schema, re-compiled independently with JavaScript's own new RegExp, and tested live as you type candidate values.

How it works

  1. Open Schema Validator, validate data with a pattern constraint in the schema.
  2. On a pattern-mismatch error, click "Test pattern" to expand an inline input.
  3. Type candidate values and see a live match/no-match against the schema's actual pattern.
  4. Adjust your data (or the schema's pattern) based on what you see.

For example, a schema with:

{
  "type": "string",
  "pattern": "^[A-Z]{2}[0-9]{4}$"
}

validated against the data "ab1234" fails with a pattern error. Expanding the tester and typing ab1234 shows no-match immediately, and typing AB1234 shows a match — making it obvious the fix is uppercasing the first two characters, not that the pattern itself needs changing.

Common pattern mistakes

  • Unanchored patterns matching more than intended. [0-9]{5} without ^ and $ matches a 5-digit substring anywhere in the string — so "abc12345xyz" passes, which is rarely what you want for a full-value check like a zip code. Anchor with ^...$ when the pattern should describe the whole string, not a substring of it.
  • Forgetting to escape a literal dot. . in regex means "any character," not a literal period — a pattern meant to require a literal . (like a simple file-extension check) needs \.. file\.txt matches "file.txt" but also note file.txt (unescaped) would match "fileXtxt" too.
  • Case sensitivity surprises. JSON Schema's pattern has no case-insensitive flag of its own — [a-z]+ won't match uppercase letters. If both cases should be valid, write [a-zA-Z]+ explicitly rather than assuming case-insensitivity.
  • Mixing up {n,m} quantifier syntax. [0-9]{4} means exactly 4 digits; [0-9]{4,} means 4 or more; [0-9]{4,8} means 4 to 8. A stray missing comma or brace silently changes the constraint rather than erroring — the live tester is the fastest way to confirm it does what you meant.
  • Assuming \d, \w behave identically everywhere. These shorthand classes work in JS regex (and in most pattern-keyword schemas) but their exact character sets (does \w include Unicode letters?) can differ subtly across regex engines — see the dialect FAQ below.

Reading a pattern-mismatch error

When validation fails on a pattern keyword, the error list shows the failing instancePath (which field), the pattern string itself, and the "Test pattern" toggle. The workflow that gets you to a fix fastest: expand the tester, paste the actual failing value from your data (not a value you assume is close), and watch whether it matches. If it doesn't, try small variants of that exact value — strip or add a character at a time — until you see where the mismatch is, rather than guessing at the whole pattern's intent from scratch. This is usually faster than reading the regex character-by-character, especially for a pattern with several groups or alternations.

Writing your own pattern from scratch

If you're writing a new pattern constraint rather than debugging an existing one, build it incrementally in the tester before saving it to the schema: start with the loosest version that captures the basic shape (e.g. ^[A-Z0-9]+$ for "uppercase alphanumeric code"), confirm it matches your known-good examples, then tighten it (add a length bound, restrict to a specific prefix) one constraint at a time — checking after each change that your known-good examples still match. Writing the full, tightly-constrained pattern in one attempt makes it much harder to tell which part of a multi-clause regex caused an unexpected non-match.

Use case: validating structured string fields

Patterns show up most often on fields that are technically strings but have real internal structure — product SKUs, postal codes, phone number formats, slugs, hex color codes. For a hex color field like "pattern": "^#[0-9a-fA-F]{6}$", the tester immediately shows why "#fff" (3-digit shorthand) fails while "#ffffff" passes — a distinction that's easy to miss just reading the regex if you're not used to counting character classes.

Frequently asked questions

Does it use the exact pattern from my schema?

Yes — the same pattern string ajv compiled, re-compiled independently with new RegExp for the live test.

What if the pattern isn't valid JS regex syntax?

The tester returns no match rather than throwing, so an edge-case pattern doesn't break the page.

Is this only for pattern errors?

Yes, it's offered specifically alongside a pattern-keyword validation error in the error list.

Will results match Python/Java/PHP's regex engine, not just JavaScript's?

Not necessarily — JSON Schema's pattern keyword is defined against ECMA-262 (JavaScript) regex syntax, which this tester matches exactly. Another language's regex engine can behave differently on the same pattern (lookbehind support, named groups, Unicode handling) — if you're validating with a non-JS library elsewhere (Python's re, Java's Pattern, C#'s Regex, PHP's PCRE), test there too rather than assuming this result transfers exactly.

Does this tester support flags like case-insensitive matching?

No — it tests the pattern string exactly as written in the schema, with no flags applied, matching how ajv itself compiles a pattern value (JSON Schema's pattern keyword has no syntax for flags). If you need case-insensitive matching, write it into the character class itself (e.g. [a-zA-Z]) rather than relying on a flag.

Why does my pattern work in a standalone regex tester but not here?

Usually one of two things: the pattern is being tested against the wrong anchoring assumption (some regex tools add implicit anchors, JS's RegExp.test() does not), or the standalone tool uses a different regex dialect (Python/PCRE) than the JS engine this tester and ajv both use.

Can I test a pattern without first triggering a validation error?

The tester is surfaced specifically alongside a pattern-keyword error in the error list, so you need a schema with a pattern and data that currently violates it to see the "Test pattern" button. Write a draft schema and a deliberately non-matching value if you want to experiment before your real data is ready.
