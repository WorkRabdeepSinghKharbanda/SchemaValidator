Generate realistic example data straight from a JSON Schema — free, in your browser, for test fixtures or demos.

Generate sample data now

Why generate sample data from a schema?

Once a schema exists, hand-writing example data that actually satisfies it is tedious and error-prone — a missed required field, a value outside an enum, or a string that doesn't match a pattern makes your own test fixture invalid before you even get to the code under test. Generating it directly from the schema, via json-schema-faker, guarantees the sample matches every constraint the schema declares — types, required, enum values, format hints, and pattern regexes are all respected, not just the top-level shape.

This is the reverse of schema inference: inference goes from data → schema, this tool goes from schema → data. Both are useful at different points — infer a schema when you only have example payloads, generate sample data when you already have (or are designing) the schema and need realistic records to work against.

How it works

  1. Open Schema Validator and paste your JSON Schema into the schema pane.
  2. Use the data pane's "⋯" menu → "Generate sample data".
  3. A generated example satisfying the schema is written into the data pane.
  4. In batch mode, generate up to 500 sample records at once for bulk test fixtures (a prompt asks for the count).

Given a schema like this:

{
  "type": "object",
  "properties": {
    "id": { "type": "string", "format": "uuid" },
    "email": { "type": "string", "format": "email" },
    "status": { "type": "string", "enum": ["active", "pending", "closed"] },
    "zip": { "type": "string", "pattern": "^[0-9]{5}$" }
  },
  "required": ["id", "email", "status"]
}

a generated sample respects every constraint at once — a real-looking UUID, an email-shaped string, one of the three allowed status values, and a 5-digit zip matching the pattern. You never have to manually satisfy the pattern or pick a valid enum value yourself.

Use cases

  • Test fixtures. Generate a handful of records that are guaranteed schema-valid, so a failing test tells you something about your code's logic, not about a fixture you typo'd by hand.
  • Seeding a local database or demo environment. Batch-generate dozens or hundreds of records matching your schema to populate a UI with realistic-looking data before real data exists.
  • Demos and screenshots. Quickly produce plausible example payloads for documentation or a product demo without inventing values field by field.
  • Sanity-checking a schema you just wrote. If generated samples look obviously wrong (every status comes back empty, every id looks identical), that's often a sign the schema itself has a mistake — generation surfaces schema bugs you might not notice just by reading the schema.

Common issues and how to read them

  • Generated values look "random" and nothing like real data. json-schema-faker fills in plausible-but-arbitrary values for anything the schema doesn't constrain tightly — a bare {"type": "string"} with no format/pattern generates a generic random string, not a meaningful one. Add format (e.g. email, date-time, uuid) or a pattern to the schema if you need more realistic-looking values.
  • An array field's generated items are all identical in shape. This matches how the schema itself is written — a single items schema applied to every array entry produces structurally uniform (though not necessarily identical-value) entries, by design; JSON Schema's items keyword describes one shape for every element unless you're using prefixItems for a tuple.
  • Batch generation stalls or feels slow near the 500 cap. 500 is a deliberate UX ceiling, not a technical hard limit — if you routinely need more, generate in a few smaller batches and combine the results, or run json-schema-faker directly in your own script for larger volumes.
  • Generation seems to ignore a constraint. Double-check the constraint is actually attached to the right node in the schema — a pattern on the parent object instead of the specific string field, for instance, has no effect on that field's generated value.

Single sample vs. batch generation

A single "Generate sample data" click is for the common case — you need one example to eyeball, paste into a test, or use as a quick demo payload. Batch mode's "Generate N samples" is a different tool for a different job: it's specifically for when you need volume — populating a table UI with dozens of rows, stress-testing a parser against hundreds of variations, or producing a CSV of fixture data. Both use the exact same generation logic underneath (schema-constrained, not hand-written), so a single sample and one row of a 500-record batch are equally valid against the schema — batch mode just runs the same generation repeatedly rather than using a different, faster, less-thorough method.

A worked example: generating fixtures for a form schema

Say you're testing a signup form's backend validation and have a schema requiring a username, an email, and an age between 18 and 120:

{
  "type": "object",
  "properties": {
    "username": { "type": "string", "minLength": 3, "maxLength": 20 },
    "email": { "type": "string", "format": "email" },
    "age": { "type": "integer", "minimum": 18, "maximum": 120 }
  },
  "required": ["username", "email", "age"]
}

Switching to batch mode and generating, say, 20 samples gives you 20 records where username is always 3-20 characters, email always looks like an email, and age is always an integer between 18 and 120 — a ready-made set of valid inputs to throw at your backend's happy-path tests, without writing any of the 20 records by hand or worrying one of them accidentally violates its own schema.

Frequently asked questions

Does the generated data always pass validation?

Yes — it's generated to satisfy the schema's own constraints (types, required fields, enums, formats).

Can I generate more than one record at once?

Yes, turn on batch mode and use "Generate N samples" (capped at 500 per generation, a sane UX limit).

Is this uploaded anywhere?

No, generation runs entirely client-side.

Does generated data respect pattern and format constraints, not just type?

Yes — enum, pattern, and known format values (like email or uuid) are all taken into account, not just the basic type.

Can I use this to seed a database or demo environment?

Yes — batch-generate as many schema-valid records as you need (up to 500 per run) and export them as JSON for seeding.

Is this the same as a JSON Schema-based mock API server?

No — this generates static example data you copy out of the data pane. It doesn't run a mock HTTP server or respond to live requests.

What if my schema has conflicting or impossible constraints?

Generation can fail or produce unexpected output if the schema itself is contradictory (e.g. a minimum greater than a maximum). Run the schema through the validator first to catch structural issues before generating from it.
