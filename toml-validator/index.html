Why validate TOML against a JSON Schema?

TOML is the config format behind Cargo (Cargo.toml), Poetry and other Python packaging tools (pyproject.toml), and plenty of app settings files that favor TOML's more explicit, less indentation-sensitive syntax over YAML. TOML's own parser catches malformed syntax — an unclosed table header, a string missing its closing quote — but not a missing required key, a wrong type, or a value outside an allowed set. A JSON Schema does, using the exact same rules you'd apply to a JSON or YAML version of the same config, which matters if your tooling needs to accept more than one config format for the same underlying settings.

TOML parses into the same kind of nested object structure as JSON or YAML once read — tables become nested objects, arrays of tables become arrays of objects — so the same ajv-based schema that validates your JSON config validates a TOML one too, with no TOML-specific schema dialect to learn.

TOML also has a couple of shorthand forms that are easy to misread as something more complex than they are: dotted keys (package.name = "foo", equivalent to a [package] table with a name key) and inline tables (point = { x = 1, y = 2 }, a whole table on one line). Both parse to the identical nested-object shape a schema would expect from the longer [package] block form — the schema doesn't need to know or care which syntax the TOML author chose.

How it works

  1. Open Schema Validator and switch the data pane's format tab to TOML.
  2. Paste or upload your JSON Schema.
  3. Paste or upload your .toml file.
  4. Errors appear with an approximate line and a plain-English explanation.

A pyproject.toml-style example — a schema requiring a package name and version, against a file missing the version:

# schema (JSON)
{
  "type": "object",
  "properties": {
    "project": {
      "type": "object",
      "required": ["name", "version"],
      "properties": {
        "name": { "type": "string" },
        "version": { "type": "string" }
      }
    }
  }
}

# data (TOML) — fails: version is missing
[project]
name = "my-package"

This reports project.version as a required property that's missing, with an approximate line near the [project] table header — the line the TOML parser itself associates with the error, which may be a line or two off from the exact key depending on how the parser reports table boundaries.

Common errors and how to read them

  • Unclosed or mismatched table headers — [project missing its closing ], or a duplicate [project] table defined twice. These are genuine TOML syntax errors and fail before schema validation even runs, with a message from the TOML parser pointing at roughly where the table header was expected to close.
  • An array-of-tables confused with a single table — [[dependencies]] (double brackets, an array of tables) vs [dependencies] (single brackets, one table). If your schema expects dependencies to be an object but the TOML uses double brackets, you'll get an array where an object was expected — check the bracket count against what your schema's type keyword actually declares.
  • A bare value that needs quoting — dates (2024-01-01) and some numeric-looking strings parse as their native TOML types (a date type, a number) rather than staying strings; if your schema expects a string and gets a type mismatch, check whether the TOML value needs explicit quotes.
  • Schema written for JSON reused as-is for TOML — since parsing produces the same object shape, a schema that already validates your JSON config should validate the equivalent TOML without changes; if it doesn't, the mismatch is almost always in how a specific value was authored in TOML (see the two points above), not in the schema itself.

Use cases

Checking a Cargo.toml against an internal schema before a crate is published internally; validating a pyproject.toml's required [project] metadata (name, version, dependencies) before a package build; and checking an app's own TOML settings file against the shape the app's config loader expects, catching a renamed or misspelled key before it silently falls back to a default value at runtime. A team standardizing config across multiple services — some using TOML, some JSON, some YAML — can also write one schema per config shape and validate every service's file against it here regardless of which format that service happens to use, rather than keeping three parallel schema dialects in sync by hand.

If your workflow is scripted rather than one-off, the schema pane's "Copy as Node.js/Python snippet" output works for a TOML check the same way it does for JSON or YAML — the snippet validates whatever parsed object you hand it, independent of which format produced that object.

Frequently asked questions

Can I validate a TOML config against a JSON Schema?

Yes — switch to the TOML tab, paste your schema, and paste or upload the file.

Exact line numbers?

Approximate, from the TOML parser's own error — JSON is the only format with exact line mapping.

Is my file uploaded anywhere?

No, everything runs client-side.

Can I validate a Cargo.toml or pyproject.toml file directly?

Yes — paste the file as-is into the data pane with the TOML tab selected. You'll need to supply your own JSON Schema describing the fields you want checked; this tool doesn't bundle a built-in Cargo or Poetry schema.

Does TOML's array-of-tables syntax work here?

Yes — [[name]] array-of-tables parse into a JSON array of objects, which a schema's "type": "array" with an items sub-schema validates the same way it would for a JSON or YAML array.

Does this support the same JSON Schema drafts as the JSON and YAML validators?

Yes — draft-07, 2019-09, and 2020-12, selected from the same dropdown used for every other format, since schema compilation doesn't depend on which data format is being checked against it.

Need a different format? Schema Validator also supports JSON, YAML, XML, and CSV against the same schema.
