XML Validator

Validate XML data against a JSON Schema — free, in your browser, no XSD required.

Validate your XML now

Why validate XML with a JSON Schema instead of XSD?

If your team already writes JSON Schemas for your JSON/YAML APIs, maintaining a separate XSD for an XML variant of the same data is duplicate work. Schema Validator parses XML into the same kind of data structure JSON produces, then runs it through the identical schema — one set of rules for every format you accept. This is not an XSD validator — if what you actually need is to check XML against an XML Schema Definition (XSD) file, this tool doesn't do that; see the FAQ below before going further.

Where this does fit even if you don't already have a JSON Schema: a quick, no-install "is this XML well-formed" syntax check works here too, with no schema pane needed at all — paste XML, leave the schema empty, and you get a plain structural check (matching tags, valid attribute syntax, one root element) without writing any schema.

How it works

  1. Open Schema Validator and switch the data pane's format tab to XML.
  2. Paste or upload your JSON Schema (optional — leave it empty for a syntax-only check).
  3. Paste or upload your XML file.
  4. Errors appear as a message list (no line number for schema-validation errors in this format) with plain-English explanations.

Attributes are parsed with an @_ prefix, so a schema has to account for that when checking an attribute rather than an element's text content:

<!-- data (XML) -->
<order id="4821">
  <status>pending</status>
</order>

// parses to:
{ "order": { "@_id": "4821", "status": "pending" } }

// schema has to match that shape:
{
  "type": "object",
  "properties": {
    "order": {
      "type": "object",
      "properties": {
        "@_id": { "type": "string" },
        "status": { "type": "string", "enum": ["pending", "shipped"] }
      }
    }
  }
}

That @_id prefix is the single most common source of a schema that "should" match but doesn't — if a property mysteriously reports as missing, check whether it's an XML attribute (needs the @_ prefix in the schema) rather than a child element (doesn't).

Common errors and how to read them

  • Mismatched or unclosed tags — <order>...</orde>. This is a genuine XML syntax error, caught before schema validation runs, and unlike a schema-validation mismatch it does get a line and column — the parser reports exactly where the malformed closing tag was found.
  • Missing or multiple root elements — XML requires exactly one root element; two sibling top-level elements with no common wrapper fail to parse. Wrap them in a single parent element.
  • An unescaped & or < inside text content — a literal ampersand in element text (<name>Smith & Co</name> written without &amp;) breaks parsing. Escape it, or wrap the text in a CDATA section.
  • A schema-validation error with no line number — once XML parses successfully, any remaining errors (wrong type, missing required field, failed enum) come from ajv checking the parsed object tree, the same as for CSV — message-only, since no line-mapping exists back to the original XML source for this format. Use the error's reported path (e.g. order/status) to find the right element by name instead of by line.

Use cases

Checking a legacy system's XML export against a JSON Schema you maintain once elsewhere (so you're not hand-writing an XSD just to cover an XML variant of an already-schema'd JSON API); a one-off "is this XML well-formed" sanity check on a file before feeding it into another tool; and validating SOAP-adjacent or config-style XML (an app's web.config-style settings file, for example) against structural rules even without a formal XSD in place.

A migration scenario worth calling out: a team moving an XML-based integration to JSON can write the new JSON Schema first, then validate the existing XML feed against the same schema to find every field-level mismatch before the consuming code switches over — rather than discovering each mismatch one bug report at a time after the cutover.

Frequently asked questions

JSON Schema instead of XSD?

Yes — XML is parsed to a plain structure and validated with the same JSON Schema rules as JSON/YAML.

Exact line numbers?

Not for schema-validation errors — those are message-only. A genuine XML syntax error (a mismatched tag) does get a line and column from the parser, before schema validation even runs.

Is my XML uploaded anywhere?

No, everything runs client-side.

I actually need to validate against an XSD, not a JSON Schema — can I use this?

No, not for that — this tool doesn't read or check against XSD files at all. If your requirement is specifically "validate this XML against an XSD," you'll need an XSD-aware validator instead. This tool is for the separate case where you already have (or want) a JSON Schema as your source of truth and need to check XML data against it too.

Can I just check if my XML is well-formed, without a schema?

Yes — leave the schema pane empty. You'll get a plain syntax/well-formedness check (matching tags, one root element, valid attribute syntax) with no need to write a schema at all.

How are XML attributes represented when validating against a schema?

Each attribute becomes a property prefixed with @_ (e.g. id="4821" on <order> becomes "@_id": "4821"), while child elements and text content keep their plain names — your schema's properties need to use that prefix for attributes.

Does this validate SOAP XML or a specific XML dialect?

It validates any well-formed XML the same way, with no SOAP-specific envelope handling — you write a JSON Schema for the structure you care about, the same as for any other XML document.

Do XML namespaces (xmlns) cause problems?

A namespace prefix becomes part of the parsed property name (e.g. <ns:id> parses to a key literally named ns:id), so a schema has to reference that exact prefixed name — there's no namespace-aware resolution that strips or rewrites prefixes before validation.
