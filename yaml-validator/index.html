YAML Schema Validator

Validate YAML configuration files, CI pipelines, or API responses against a JSON Schema — free, in your browser, with no data ever leaving your device.

Validate your YAML now

Why validate YAML against a JSON Schema?

YAML is the default format for Kubernetes manifests, GitHub Actions workflows, OpenAPI specs, and countless app config files — but YAML's own syntax rules won't catch a missing required field, a wrong type, or a typo'd enum value. A JSON Schema catches exactly those mistakes, and the same schema can validate both your YAML and JSON representations of the same data.

Under the hood this works because YAML is a superset of what JSON Schema cares about: once parsed, a YAML document is the same kind of nested object/array/string/number structure a JSON document would produce, so the identical ajv engine and identical schema validate either one. You don't maintain a YAML-specific schema and a JSON-specific schema separately — one schema covers both.

How it works

  1. Open Schema Validator and switch the data pane's format tab to YAML.
  2. Paste or upload your JSON Schema in the schema pane (JSON Schema is always authored as JSON, even when validating YAML data).
  3. Paste or upload your YAML file in the data pane.
  4. Errors appear inline with an approximate line number, plus a plain-English explanation of what's wrong.

A Kubernetes-style example — a schema that requires a container's resource limits, and a manifest fragment that's missing them:

# schema (JSON, as always)
{
  "type": "object",
  "properties": {
    "resources": {
      "type": "object",
      "required": ["limits"],
      "properties": {
        "limits": { "type": "object", "required": ["cpu", "memory"] }
      }
    }
  },
  "required": ["resources"]
}

# data (YAML) — fails: limits is missing entirely
resources:
  requests:
    cpu: "250m"
    memory: "64Mi"

This reports resources.limits as a missing required property, with an approximate line pointing near the resources: block — close enough to navigate to, though not the exact line JSON gets, since the error is mapped from the parsed data tree rather than YAML's own source positions.

Common errors and how to read them

  • Indentation mismatch — YAML is whitespace-significant; a key indented one space off from its siblings either attaches to the wrong parent or throws a parse error outright (bad indentation-style messages from the YAML library). Since YAML parse errors are approximate, check a few lines around the reported one, not just that exact line.
  • Tabs instead of spaces — YAML disallows tab characters for indentation; a file edited in a tab-indenting editor often fails to parse with a message about an unexpected character, even though it looks fine visually.
  • An unquoted value that YAML "helpfully" reinterprets — version: 1.20 parses as a number, truncating a semantic-version-looking string; enabled: yes parses as a boolean. If your schema expects a string and the data looks right but fails with a type error, this is almost always why — quote the value (version: "1.20") to force it to stay a string.
  • A schema mismatch that's really a structural difference — e.g. a Kubernetes manifest with multiple documents separated by ---. This parser reads one YAML document per validation — a multi-document file needs each document validated separately (split and paste one block at a time, or validate the first and reuse the process for the rest).

Use cases

Common real uses: checking a Kubernetes Deployment or ConfigMap against an internal schema before applying it with kubectl; validating a GitHub Actions workflow file's structure against a schema you maintain for your org's conventions; linting an app's config.yaml against the shape the app's code actually expects, to catch a typo'd key before a deploy; and checking an OpenAPI 3.x spec authored in YAML — for the OpenAPI-specific schema extraction and $ref handling, see the OpenAPI validator page instead of hand-writing that schema yourself.

For a recurring check rather than a one-off paste, the schema pane's "Copy as Node.js/Python snippet" produces a self-contained script that loads the YAML file with the same library this tool uses and runs it through ajv — a reasonable stopgap for a pre-commit hook or a CI step, short of maintaining a dedicated CLI.

Frequently asked questions

Can I validate a YAML file against a JSON Schema?

Yes — pick the YAML tab, paste your schema, and paste or upload your YAML file. Validation runs the same ajv engine used for JSON.

Does my YAML get uploaded to a server?

No. Everything runs client-side in your browser. Nothing you paste or upload is sent to a server.

Which JSON Schema drafts are supported?

Draft-07, 2019-09, and 2020-12 — switchable, or auto-detected from the schema's $schema field.

Is there a CLI version for CI pipelines?

Not built — this is intentionally a browser-only tool, no CLI or npm package. For CI, use the schema pane's "Copy as Node.js/Python snippet" feature to get a self-contained script that runs the same check outside the browser, including against Kubernetes manifests or any other YAML config.

Can this validate Kubernetes manifests specifically?

Yes, in the sense that a manifest is just YAML — write (or find) a JSON Schema describing the fields your team requires on a Deployment/Service/ConfigMap and validate against it here. This tool doesn't ship built-in Kubernetes API schemas; you supply the schema.

Do I get exact line numbers for YAML errors, like I do for JSON?

No — YAML gets an approximate line number from the YAML library's own error object, not the exact line/column mapping JSON gets. It's close enough to find the right area of the file, not a precise marker.

Is "lint YAML" the same thing as "validate YAML against a schema" here?

In this tool, yes — there's no separate style/formatting linter (trailing whitespace, key ordering); what's offered is schema validation, which also happens to be what most people mean by "lint my YAML" when they're checking a config file's correctness rather than its formatting.
